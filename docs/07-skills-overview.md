# 07 — Skills Overview

Claude Skills — папки с `SKILL.md` (+ опционально скрипты, шаблоны), расширяющие Claude
сфокусированными процессами для частых задач: планирование, ТЗ, QA, deploy.

## Skills — это роли внутри пайплайна

Skills не заменяют цикл эпика ([PIPELINE.md](../.claude/PIPELINE.md)) — они роли, которые
оркестратор надевает по ходу цикла. `/fitch` — точка входа в проработку эпика, и ведёт его сам
оркестратор, а не отдельный человек-техлид. Multi-role audit — не отдельно вызываемый skill: self-audit
A–G гоняет свежий adversarial-субагент внутри `/fitch`-цикла, до первой волны ([PIPELINE.md §6](../.claude/PIPELINE.md)).
Pre-epic prep skills собирают фактуру о реальном состоянии кода **до** брифа — вход в `/fitch`, а не
его часть.

## Главное правило

**Перед использованием skill'а — прочитать его `SKILL.md` целиком.** Не угадывать содержимое по
названию или предыдущему опыту: skills эволюционируют, актуальная информация — в файле, не в памяти.

## Референсный набор ролей

| Skill | Когда | Что делает | Output |
|---|---|---|---|
| `/fitch` | UI/feature/security эпик с трассируемостью требований до тестов | Контракт `contract.json`, роли analyst → designer → tech_lead → toster → devops по очереди | `FITCH-PLAN.md` + контракт, готовый для `/tech-lead` |
| audit (внутри fitch) | Перед W1 любого нетривиального эпика | Свежий adversarial-субагент проверяет контракт/план семью линзами (self-audit A–G) | Отчёт находок, свёрнутый до старта волн |
| `/tech-lead` | После fitch, план готов к исполнению | Декомпозиция плана в `PLAN.md` + `task-NN-*.md` с волнами | Самодостаточные task-файлы для субагентов |
| `/toster` | Эпик требует структурированной приёмки | Матрица требование → тест, конкретные команды с ожидаемым выводом | Чеклист приёмки, не субъективное «работает» |
| `/dev-ops` | Эпик трогает build/installer/deploy | План версии + сборки + rollback | Финализационный task с явными командами |
| `/pm` | Абстрактная задача без готового плана ролей | Сам решает, какие роли нужны и в каком порядке, ведёт до артефактов | Полный комплект: brief/fitch/PLAN/task-файлы/приёмка |
| `/ba-spec` | Нужно ТЗ/требования к фиче | Полноценное ТЗ с учётом существующего кода | ТЗ-документ для `/tech-lead` |
| `/ui-designer` | Жалоба на UI, нужна точечная правка | Читает дизайн-систему, формулирует проблемы, правит только токенами проекта | Конкретные правки + обоснование |

## Доменные skills

Помимо ролей пайплайна, у каждой зоны продукта может быть свой **доменный скилл** — не роль в
процессе, а знание конкретной зоны: инварианты, специфичные ловушки, конвенции модуля. Оркестратор
читает доменный скилл своей зоны **перед** первой правкой в ней, отдельно от `/fitch`/`/tech-lead`.
Доменные скиллы могут быть многоуровневыми (общий скилл зоны → более узкий скилл подзоны, читается
после общего). Кандидат на доменный скилл — зона, где типовая ошибка новичка стабильно повторяется
через несколько эпиков; до этого порога знание живёт в `CLAUDE.md` зоны, не в отдельном skill'е.

## test-authoring — канон качества тестов

Отдельный skill, не привязанный к конкретному эпику: чеклист авторинга и ревью unit-тестов (доли
oracle/mutation/negative/edge/structural покрытия, антипаттерны ассертов). Применяется при написании
новых тестов, ревью PR с тестами и самооценке тестового пакета — **во время или после** реализации,
не на этапе планирования, в отличие от `/fitch`/`/tech-lead`.

## Kit skills — для внешних участников

Публичный набор `kit/skills/*/SKILL.md` — не роли внутреннего пайплайна, а пошаговый цикл для
контрибьютора вне основного контура (человек, человек с ассистентом, автономный агент): взять задачу
→ развернуть окружение → сделать и прогнать гейты → оформить PR с доказательствами. Читаются строго
по порядку, каждый ссылается на следующий:

1. `kit/skills/take-task/` — найти источник задачи, разведать зону кода, зафиксировать план и
   критерии готовности до первой правки.
2. `kit/skills/setup-env/` — окружение с нуля: клон, ветка, зависимости, собственный мок-стенд.
3. `kit/skills/implement-and-gates/` — малые проверяемые шаги, полный набор гейтов перед PR.
4. `kit/skills/pr-with-proofs/` — PR с доказательствами: прогоны текстом, самопроверка утверждений.

Канон и полный порядок чтения комплекта — `kit/README.md`.

## Композиция skills

Стандартный feature-эпик проходит роли последовательно:

```
владелец формулирует цель
  → /fitch (внутри: analyst → designer → tech_lead → toster → devops) + self-audit A-G
  → /tech-lead → PLAN.md + task-файлы
  → волны: оркестратор → субагенты по task-файлам (доменный skill зоны — перед первой правкой в ней)
  → /toster → приёмка
  → финализация: версия + docs + close
```

Роли идут последовательно (хотя субагенты внутри волны — параллельно). Несколько ролей над одним
scope параллельно теряют согласованность: например designer строит на версии ТЗ, которую analyst уже
переписал.

## Когда skill не нужен

1. **Hotfix.** Баг найден, фикс очевиден — один task без fitch/audit.
2. **Cleanup-эпик.** Disk wipe, archive moves, docs refresh — см. `08-housekeeping-and-pre-flight.md`.
3. **Известный паттерн.** Пятый однотипный эпик («добавить импортёр для X») не требует full fitch —
   копируется паттерн предыдущего.
4. **Discovery/spike.** Нужно понять «возможно ли» — один субагент с task'ом «изучи, напиши отчёт».

## Skills и память

Skills не хранят состояние между сессиями — каждый запуск читает `SKILL.md` заново, что позволяет
улучшать skill без риска для legacy-поведения. Память техлида хранит **проектные правила** (task-format,
инварианты, схема работы), не skill-specific детали: skills — generic instrumenты, правила проекта —
их конкретное применение.

## Создание новых skills

Паттерн, повторившийся 3+ раза и стабилизировавшийся — кандидат на skill: `SKILL.md` (когда/что/как) +
опционально скрипты и шаблоны output'а. До этого порога паттерн живёт в `.claude/templates/` или в
`WORKFLOW.md`.

## Анти-паттерны

1. **Skill без чтения SKILL.md** — теряются его актуальные правила.
2. **Skill вызывается «потому что есть».** Для тривиальной задачи запускается `/pm`, который тянет
   ещё четыре роли — минуты вместо секунд.
3. **Output skill'а игнорируется.** Владелец не читает `FITCH-PLAN.md`, решает «давай по-другому»; в
   плане уже было предупреждение про этот случай.
4. **Output не сохраняется в репозиторий.** Правки ad-hoc теряют trail — все output'ы живут в
   `.claude/fitch/<epic-id>/`.
5. **Несколько ролей параллельно над одним scope** — теряется согласованность между их артефактами.

## Минимальный набор для нового проекта

Если не хочется сразу разбираться со всем набором — минимум:

1. `/fitch` — структурированная проработка (self-audit A–G внутри цикла, не отдельный skill).
2. `/tech-lead` — декомпозиция в task-файлы.
3. `/toster` — приёмка.

Остальные подключаются по мере роста проекта.
