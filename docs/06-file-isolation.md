# 06 — File Isolation in Waves

Главный инвариант параллельного выполнения. Без file isolation параллельные субагенты устраивают
git race и портят работу друг друга. С ней — экономия в разы против последовательного выполнения
той же волны.

## Правило

**Два субагента не трогают один файл в одной волне** — даже если они правят разные функции в нём.
Иначе race на read-modify-write через git.

Что считается «трогать»: правка, перезапись, перемещение/переименование, удаление. Что не считается:
чтение, просмотр, проверка метаданных файла. Читать параллельно безопасно, писать — нет.

## Почему именно так

Субагенты работают через git commits, не через общую память. Если два субагента параллельно правят
один файл: оба тянут исходное состояние, оба редактируют независимо, оба коммитят. При слиянии их
веток — конфликт; если он автоматически резолвится — теряются изменения одного из них; если не
резолвится — кто-то должен мержить руками. Оба исхода — нарушение изоляции.

В последовательном варианте (один субагент после другого в той же волне) — A коммитит, B тянет
свежее состояние, видит изменения A, правит поверх них, коммитит. Race нет.

## Резолвы конфликтов

**Sequential в одной волне.** Один субагент делает task-A, потом task-B на тот же файл; остальные
task'и волны идут параллельно. Применяется, когда два task'а трогают один файл, логически связаны
(например diag + fix одного модуля), а разносить на волны — overhead.

**Перенос task'а в следующую волну.** Task-B уходит в W+1: в W субагент A работает один над файлом,
в W+1 субагент B стартует со свежего состояния. Применяется, когда task'и независимы, а
sequential-исполнение в одной волне раздувает её время; либо когда task-B по смыслу зависит от
пост-волнового machine-DoD verify task-A ([PIPELINE.md §7](../.claude/PIPELINE.md)), а не от
чат-подтверждения между task'ами — такого подтверждения в автономном цикле нет.

**Декомпозиция файла до старта эпика.** Если файл «гравитирует» все task'и (точка входа приложения,
менеджер-синглтон, центральный конфиг) — декомпозировать на 2-3 модуля до старта, как pre-flight
housekeeping'а. Применяется, когда файл — хронический источник конфликтов через несколько эпиков, и
декомпозиция архитектурно валидна.

## Audit перед стартом эпика

Проверка file isolation обязательна **до** финализации плана волн. Три способа:

1. **Grep по task-файлам:** `grep -l "<путь к файлу>" .claude/tasks/<epic-id>/task-*.md` —
   если возвращает больше одного task'а внутри одной волны, конфликт резолвится до старта.
2. **Build matrix** — таблица «файл × task × волна»: конфликт, если один файл фигурирует у двух
   task'ов одной волны; несколько task'ов одного файла в разных волнах — норма.
3. **Явная секция аудита в контракте** (`file_isolation_audit: { passed, conflicts_resolved: [...] }`)
   — заставляет план явно зафиксировать, что проверка проведена и как разрешён каждый конфликт.

## Особый случай — точка входа приложения и общие exposes

В большинстве проектов одна точка становится attractor'ом изменений: главный компонент приложения,
точка входа бэкенда, корневой обработчик. Любой task, добавляющий тестовый hook, новый провайдер
состояния или глобальный обработчик, хочет зайти именно туда.

**Решение: централизовать все exposes в один task в первой волне.**

```typescript
// task-02 W1 — все exposes за один проход
if (import.meta.env.MODE === 'test' || (window as any).__E2E__) {
  (window as any).__APP_STORE__ = useAppStore;
  (window as any).__ENTITY_MANAGER__ = entityManager;
  (window as any).__ENTITIES_STORE__ = useEntitiesStore;
  (window as any).__FEATURE_STORE__ = useFeatureStore;
  (window as any).__HISTORY_MANAGER__ = historyManager;
}
```

Все остальные task'и волны **только используют** exposes (`window.__APP_STORE__.getState()`), не
трогают точку входа. Один task — один файл — нет race.

## Ownership declarations across tasks

Субагенты изолированы: каждый видит только свой task-файл и промпт оркестратора, не читает чужие
task'и и не видит общий план. Значит owner конфликтного файла должен быть прописан **в каждом
заинтересованном task-файле явно**, а не только в плане волны.

**В task-файле владельца файла** — явно: «редактируем этот файл, ownership на нас».

```markdown
## Контекст
T04 владеет `backend/skills/mod.rs` в этой волне — добавляет декларации сразу для всех новых
скиллов волны, включая те, что реализуют T05/T06. T05 и T06 НЕ редактируют mod.rs.
```

**В task-файлах остальных** — явный запрет с указанием владельца: «НЕ редактировать
`backend/skills/mod.rs` — им владеет T04, декларация уже добавлена».

**Выверка после волны** — `git log --oneline -- backend/skills/mod.rs`: ожидаемо один коммит из
волны; два и больше — нарушение изоляции, эскалация.

Анти-паттерн: владелец объявлен только в плане волны/промпте оркестратора, но не в самих
task-файлах. Субагент, не видящий план, «улучшает заодно» и редактирует чужой файл. Дублирование
«T04 владеет mod.rs» в каждом заинтересованном task-файле — не избыточность, это единственный
источник истины, который вообще увидит субагент.

## Что считается «один файл» и granularity внутри файла

Один файл — один путь. `src/App.tsx` и `src/App.test.tsx` — разные файлы, параллельно безопасно;
`backend/main.rs` и `backend/lib.rs` — тоже разные. Изоляция действует на уровне файла целиком: даже
если task-A правит функцию `foo()`, а task-B — функцию `bar()` в том же файле — это конфликт, потому
что правки применяются на уровне текста, не AST, и per-function lock невозможен. Если очень нужно
править разные функции одного файла параллельно — декомпозировать файл на модули заранее.

## Edge cases

- **Append-only файлы (CHANGELOG.md).** Технически конфликт — два append'а в одной волне гонятся.
  Практически такие обновления не делаются параллельными субагентами: CHANGELOG правится в task'е
  финализации волны, не в фичевых task'ах.
- **Machine-generated файлы (lock-файлы).** Автообновляются при установке зависимостей; параллельная
  установка разных зависимостей гонится на lock-файле. Решение — установка/обновление зависимостей
  отдельным task'ом в первой волне, не «между делом» в фичевых task'ах.
- **Автогенерируемые исходники (протокольные схемы и т.п.).** Тот же класс, что lock-файлы — один
  task на регенерацию, остальные используют результат.
- **Общий тестовый файл на несколько фич.** Если две фичи одной волны делят один spec-файл — либо
  sequential, либо развести на отдельные spec-файлы (обычно фичи и так разнесены по файлам, конфликт
  редок).

## Изоляция рабочих каталогов

Отдельный от file isolation инвариант — не файл внутри дерева, а само рабочее дерево целиком. Полный
канон — [RULES.md R7](../.claude/RULES.md); здесь — как это связано с волной.

- **Один каталог — один владелец.** Каталог принадлежит ровно одному активному агенту/эпику;
  переключение чужой ветки в нём запрещено, включая «на минутку».
- **Параллельная работа — только через worktree.** Второй контур (ревью чужого PR, вторая цепочка,
  соседний эпик) получает собственный `git worktree`, не переключает ветку в общем дереве.
- **Pre-flight — сверка ветки.** Первое действие сессии — сверить текущую ветку с ожидаемой.
  Расхождение — **СТОП и доклад**, не молчаливый возврат ветки на место: рядом уже работает кто-то.
- **Финишное состояние.** По завершении дерево остаётся либо на своей ветке, либо worktree снят.
  «Оставил на общей ветке» — следующий агент прочитает это как разрешение работать здесь.
- **Прерванная операция — всегда доклад.** Обрыв связи, конфликт слияния, исчерпанный лимит —
  СТОП-доклад о фактическом состоянии, не брошенная операция без объяснения
  ([RULES.md R7](../.claude/RULES.md)).

## Два исполнителя в одном дереве

Когда два субагента пишут в одно рабочее дерево последовательно в пределах сессии (не параллельно —
см. «Правило» выше), риск смещается с git race на захват чужих изменений при стейджинге: каждый
коммит стейджит **непересекающиеся pathspec'ы**, перед стейджингом — `git status --porcelain`, а
`git add -A` в этом сценарии запрещён — он молча прихватывает чужие незакоммиченные правки в чужой
коммит.

## Швы между параллельными линиями

Когда рядом растёт вторая линия разработки (второй участник, второй контур), точки, которые обе
линии структурно гарантированно затронут (диспетчерские таблицы, перечисления, switch-ветки),
подчиняются правилу «только добавлять в конец, никогда не редактировать чужую ветку», а каждое
слияние такого шва проходит аудит удалённых строк против обеих сторон; если два блока кода попадают
в одну и ту же точку шва — надёжное разрешение — реплей хунков каждой стороны поверх общей базы
слияния (base-coordinate merge). Полный контракт (резервации, запретные зоны, каденция ребейза,
«кто готов — тот первый») — [docs/13](13-merge-trains-and-parallel-lines.md).

## Что делать, если file isolation нарушен

Признаки: конфликт при попытке слияния, пропавшие изменения одного из субагентов, предупреждение о
непреднамеренном мерже.

1. **Стоп волну** — не продолжать до резолва.
2. **`git log <file>`** — какие коммиты волны затронули файл.
3. Если коммиты накладывают **разные** изменения — смёржить руками, проверить, что обе правки
   работают.
4. Если коммиты перекрывают **одну и ту же** строку — выбрать корректный коммит, второй откатить и
   переписать.
5. Эскалация в план волны — что было упущено в audit'е file isolation, чтобы не повторилось.

## Связь с другими инвариантами

- **DoD per task** — без изоляции task проверяет DoD на чужих изменениях и получает ложный зелёный.
- **Machine-DoD verify между волнами** — race между волнами предотвращается тем же принципом
  изоляции, даже без чат-подтверждения.
- **Build wrapper-скрипты** — если субагенты параллельно ставят зависимости напрямую, lock-файлы
  гонятся; обёртки централизуют установку и исключают race.
