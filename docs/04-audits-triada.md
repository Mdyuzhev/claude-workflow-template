# 04 — Аудит-триада

Один принцип триангуляции, применяемый в трёх разных контекстах цикла. Формальное правило —
[RULES.md R9](../.claude/RULES.md#r9-целостность-гейтов-четыре-правила) (гейты); здесь — сама
механика аудита людьми/субагентами, не машинными гейтами.

## Три контекста аудита

1. **Рекон-рой внутри оркестратора, до фитча** ([PIPELINE.md §3](../.claude/PIPELINE.md#3-рекон),
   [02-epic-lifecycle.md Шаг 3](./02-epic-lifecycle.md#шаг-3--рекон)) — рой независимых
   Sonnet-субагентов по осям брифа, triangulation (3+ согласны = твёрдая находка), обязательный
   adversarial-разбор для любого утверждения об отсутствии («X не существует», «дефект не найден») —
   один grep не доказывает отсутствие, нужен grep по всему дереву плюс проверка регистраций/wiring
   плюс поиск stub/мёртвого кода. REQUEST-шаблон рою —
   [recon-request.md](../.claude/templates/recon-request.md): мандат + верифицированные seed-якоря +
   оси + правило триангуляции + инварианты + out-of-scope + формат фактуры.
2. **Self-audit A–G свежим adversarial-субагентом, до W1** ([PIPELINE.md §6](../.claude/PIPELINE.md#6-self-audit-ag--фолд),
   промпт — [fitch-audit-prompt.md](../.claude/templates/fitch-audit-prompt.md)) — семь направлений
   ниже, HIGH = блокер старта волн с `file:line` и конкретной правкой. Фолд HIGH/MED в
   `contract.json`/task-файлы — ВСЕГДА полная перезапись файла, никогда построчная правка (ломает
   структуру JSON).
3. **In-flight триада** (этот документ, ниже) — architect/engineer/skeptic (+опц.
   security/qa) на готовый код или артефакт, на любой стадии: ревью модуля, аудит чужого fitch'а,
   проверка перед merge.

Внешний audit-рой сторонним провайдером в цикле не требуется — все три контекста ведёт сам
оркестратор Sonnet-субагентами; отдельная read-only внешняя сессия остаётся опциональным
инструментом для дорогих discovery-проходов, не обязательным звеном цикла.

Оба первых контекста и in-flight триада — один и тот же принцип триангуляции (3+ согласны = твёрдая
находка), различие — в том, ЧТО смотрят: рекон — на поверхность эпика и код ДО плана, self-audit —
на готовый пакет плана ДО кодинга, триада — на готовый код или артефакт.

## Направления self-audit A–G

| # | Направление | Что ловит |
|---|---|---|
| A | Coverage | каждое требование покрыто задачей И QA-проверкой; нет требований без задачи и задач без требования |
| B | Feasibility | сигнатуры и пути сверены с реальным кодом на диске; DoD-команды исполнимы |
| C | File isolation | один owner на файл; нет двух задач на один файл в одной волне |
| D | Waves | волновая разбивка верна; зависимости между задачами не нарушены; параллельные группы реально параллельны |
| E | DoD-greps | **false-green hunt** — грепы, которые проходят, хотя фичи нет, или таргетят несуществующую/перефразированную строку |
| F | Invariants | неприкосновенные инварианты проекта не нарушены пакетом |
| G | Missing edges | упущенные грани, дефекты, которые вносит сам план |

## Роли in-flight триады

### Architect

Структурный фокус: архитектура, слои, абстракции, single responsibility, изоляция файлов, контракты
между модулями. Игнорирует мелкие баги. Пример находки: один файл-точка входа правится в шести
задачах из пяти разных волн (нарушение изоляции); модуль пайплайна нарушает чистоту прямым чтением
глобального состояния хранилища.

### Engineer

Реализационный фокус: конкретные баги, сигнатуры типов, граничные случаи, гонки, неверные вызовы
API. Пример: якорь правки использует отступ, которого нет в реальном файле; нативная сборка вызвана
напрямую в обход обёртки проекта.

### Skeptic

Композиция и REJECT-фильтр: «это вообще нужно?», «не theatre ли?», cost-benefit. Особенно ценен в
backlog'е — отсекает теоретические дефекты, не материализующиеся в реальном использовании. Пример:
находка про состояние гонки между двумя подсистемами, которое реально возникает только при не
поддерживаемом продуктом сценарии — в backlog, не блокер.

### Security (опционально)

OWASP-фокус: threat model, exploit-цепочки, защита данных, supply chain. Пример: маскирование в логе
пропускает один конкретный заголовок с чувствительными данными.

### QA (опционально)

Фокус на пробелах покрытия: матрица покрытия, слабые ассерты, отсутствие враждебных фикстур, риск
флейка на baseline. Пример: задача с тестами физически отсутствует в пакете — часть требований без
gate-теста.

## Triangulation rule

- **3+ источника** = твёрдый блокер — чинить обязательно перед merge.
- **2 источника, верифицировано оркестратором/техлидом** = probable, P1.
- **1 источник, верифицировано** = solo, P2 или backlog.
- **1 источник без verification** = backlog/dropped, ответственность за follow-up на владельце.

Один субагент защищает первое пришедшее в голову объяснение; если тот же finding пришёл от двух
независимых ролей — совпадение маловероятно, finding реален. Solo-находки не отбрасываются —
верифицируются чтением реального кода; если подтверждены, это реальный, просто более узкий finding.

### Composition bugs

Отдельная категория — находки из разных аудитов (разных модулей), которые складываются в цепочку
атаки, не будучи триангулированы в одном проходе. Пример: враждебный импорт → выполнение скрипта в
песочнице → path traversal в form-данных → XSS через отключённый CSP — каждый компонент найден
отдельно и некритичен, вместе — компрометация в один клик. Триангуляция не ловит это автоматически —
нужен отдельный synthesis-проход поверх находок всех ролей в поиске cross-cutting паттернов.

## Scope sizing

| Масштаб | Состав | Wall-clock | Применение |
|---|---|---|---|
| Mini | 1 роль | 5-15 мин | один файл/функция |
| Small | 2 роли (architect+engineer) | 30-60 мин | один модуль, 5-10 файлов |
| Medium | 3 роли (+skeptic) | 1-2 часа | фича/эпик, 20-50 файлов |
| Large | 5 ролей (+security+qa) | 2-4 часа | multi-module, fitch эпика |

Wall-clock параллелен (роли стартуют одновременно), синтез — после. Неочевидный scope — брать
Medium по умолчанию: лучше переборщить с ролями, чем пропустить блокер.

## Процесс полного цикла

1. **Подготовка scope** — что аудируется, какой scale, какие роли, что им читать.
2. **Параллельный запуск** — каждая роль получает: что читать, роль, формат вывода (`id`
   `one-line` / `where` / `risk` / `fix`).
3. **Синтез** — находки собираются в один отчёт по шаблону
   [audit-report.md](../.claude/templates/audit-report.md): триангулированные (блокеры) → probable
   (P1) → solo (P2) → REJECT под сомнением (роли разошлись) → backlog/dropped. Каждая находка несёт
   `<refs>` — какие роли согласились.
4. **Reject pass с владельцем** — по каждому блокеру: реальный ли эксплойт/impact, оправдана ли цена
   фикса, в скоупе ли текущего эпика. Skeptic-фильтр на этой стадии важен — не каждый finding нужно
   чинить здесь и сейчас; theatre-находки отбрасываются явно с причиной.
5. **Применение** — approved-находки правят fitch/task-файлы/контракт мини-волнами ДО W1: переписать
   task с phantom-сигнатурой, создать физически отсутствующую задачу, обновить file isolation,
   зафиксировать deferred-пункты в реестре.

## Когда аудит нужен, когда нет

**Нужен:** medium/large эпик (15+ задач); security-чувствительный эпик; эпик с накопленным
audit-долгом; перед merge крупного рефакторинга.

**Не нужен:** hotfix (1-2 задачи); косметика/UX-полировка; housekeeping между фичами.

Решение — оркестратор с обоснованием; если владелец явно просит пропустить аудит — риск на
владельце, фиксируется отдельной строкой.

## Приёмка внешней работы — отдельный документ

Аудит из этого документа проверяет план/код ДО или ВО ВРЕМЯ работы над своим эпиком. Проверка
результата, сданного внешним контуром или внешним участником («делать больше нечего», открытый PR),
— отдельный процесс с независимым перегоном гейтов и раундами ACCEPTED/NOT ACCEPTED, канон —
[11-acceptance-and-final.md §3](./11-acceptance-and-final.md#3-приёмка-внешней-работы-лидом).

## Антипаттерны

1. **Аудит одной ролью** — теряется триангуляция, находки субъективны. Минимум две роли.
2. **Аудит без verification находок по коду** — половина находок субагента на практике — угадывание
   по памяти, а не факт.
3. **Аудит без reject pass с владельцем** — всё идёт в фикс, чинится theatre, эпик разрастается.
4. **Composition bugs пропущены** — каждая роль смотрит на свой модуль, cross-module цепочку не
   видит никто без отдельного synthesis-прохода.
5. **Backlog-находки забыты навсегда** — solo-finding задокументирован, но никогда не пересмотрен;
   решение — регулярно ревьюимый пул отложенного.
6. **Аудит становится вечным блокером** — каждый finding обязан быть закрыт перед merge, эпик не
   закрывается; только триангулированные блокеры обязательны, остальное приоритизируется по
   cost-benefit.
7. **Инвентарь одним субагентом вместо роя** — единственная точка зрения на «что вообще есть в
   коде» пропускает то, что видно только с другого ракурса; inventory одного аудитора — стартовая
   точка для grep-verify, не готовый факт.
8. **Absence claim без adversarial-опровержения** — «фичи X нет» / «дефект не воспроизводится»,
   принятое по одному подтверждающему проходу, без отдельной попытки его опровергнуть, — не выше
   solo-находки по правилу триангуляции.
9. **Severity, аргументированная через PoC, а не через reachability в реальном использовании** —
   демонстрация «это можно вызвать» без проверки, вызывается ли это в реальном пути пользователя,
   даёт неверную приоритизацию находки в обе стороны — как завышенную, так и заниженную.
