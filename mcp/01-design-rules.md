# 01 — Design Rules for Project MCP Servers

Канонический дом сквозных правил дизайна для любого MCP-сервера проекта. Каждое правило
выведено из реального дефекта, найденного на ревью или на живом инциденте, и одинаково
применимо к серверу на любом стеке — это дизайн, не код. Формат каждого пункта: правило ·
почему (обобщённый прецедент) · как проверить.

## Протокол и транспорт

**Один транспортный модуль на все серверы.** Несколько серверов используют общий модуль
JSON-RPC-over-stdio вместо того, чтобы каждый заново реализовывал `initialize`/`tools/list`/
`tools/call`. *Почему:* до объединения один и тот же протокольный баг находили и чинили
независимо в каждом сервере. *Проверка:* общий wire-suite проходит против каждого сервера
без изменений в самом наборе.

**Согласование версии протокола, а не отказ.** На `initialize` сервер эхует запрошенную
версию, если она поддерживается, иначе отвечает своей САМОЙ НОВОЙ поддерживаемой — никогда
ошибкой. *Почему:* прецедент — жёсткий список «поддерживаю только эти версии» разом положил
несколько серверов, когда клиент обновился и стал запрашивать более новую версию, не
связанную с реальной функциональностью. *Проверка:* проба живости шлёт версию новее любой
известной — сервер обязан согласовать, а не отказать.

**Рукопожатие обязательно, ошибки — по классам.** `initialize` обязателен до `tools/call`/
`tools/list` (вызов до рукопожатия — протокольная ошибка, не крах); неизвестный инструмент →
`isError:true`, а не протокольная ошибка; отсутствие имени инструмента вовсе — протокольная
ошибка; batch, если не поддерживается, — явный отказ, никогда молчаливая обработка первого
элемента. *Почему:* смешение классов «isError» и «транспортная ошибка» ломает retry-логику
и сводку у каждого клиента. *Проверка:* wire-suite покрывает все случаи явно.

## Конфигурация и деградация

**Graceful degradation.** Протокольный цикл стартует ВСЕГДА; отсутствующий конфиг — внятная
ошибка на конкретном `tools/call`, не крах на старте. *Почему:* сервер, падающий до старта
цикла, ломает сессию каждому, у кого конфиг ещё не заведён — а при регистрации в общем
клиентском конфиге он не заведён у всех, кроме автора. *Проверка:* пустой конфиг —
`initialize`/`tools/list` живы, падает только зависимый вызов.

**Пути — только через `fileURLToPath()`.** Никогда через `URL.pathname`. *Почему:* на
Windows `pathname` даёт путь с ведущим слэшем перед буквой диска — проверка существования
файла по такой строке тихо всегда ложна. *Проверка:* юнит-тест на Windows-подобном значении
`import.meta.url`, не только POSIX.

**Таймаут на каждый сетевой вызов.** *Почему:* в долгоживущем процессе один зависший запрос
без таймаута замораживает вызов навсегда, а иногда и соседние. *Проверка:* мок, никогда не
резолвящий промис, — вызов всё равно завершается по таймауту понятной ошибкой.

## Честность превью и тестов

**`dry_run` честный и симметричный.** Строится тем же кодом и теми же аргументами, что
реальный вызов, отличаясь только пропуском финального шага с побочным эффектом. *Почему:*
превью на отдельном упрощённом пути расходится с реальностью. *Проверка:* оба режима
проходят через одну функцию вплоть до различающей их последней строки.

**Тесты мутаций сравнивают URL целиком.** Мок на «содержит» не отличает верный путь от пути
со сдвоенным префиксом. *Почему:* класс «верный суффикс, неверный префикс» невидим тесту на
«содержит». *Проверка:* точное сравнение полного URL в assert, никогда substring.

**`.gitignore`-миграции — с compat-строками.** Старые паттерны кред-путей остаются в файле
при переносе. *Почему:* иначе у тех, кто на старой раскладке, живые креды становятся
untracked-кандидатом на массовый `git add`. *Проверка:* старый путь всё ещё в `.gitignore`
после миграции.

## Экономика результата

**`tools/list` держат компактным.** Описание — одно предложение; проза уезжает в
документацию. *Почему:* измерено — список инструментов был в разы больше необходимого, и
эту цену платит каждая сессия до первого вызова. *Проверка:* байтовый размер сериализованного
`tools/list` до/после диеты.

**Сводка по умолчанию, деталь — опт-ин.** Крупный результат (полный прогон, полный отчёт) —
компактная сводка по умолчанию, построчная деталь — явный параметр. *Почему:* измерено —
полный результат на порядок тяжелее нужной вызывающему сводки, и цена платится на каждом
вызове. *Проверка:* сравнить размер ответа по умолчанию и с опт-ином на одном прогоне.

## Долгие операции

**Детач-процесс + сентинел на диске.** Статус/лог/сентинел завершения — файлы в каталоге
запуска, не память сервера. *Почему:* рестарт MCP-канала посреди операции не должен выглядеть
как её исчезновение и провоцировать повторный запуск ещё идущей работы. *Проверка:* убить
процесс сервера во время операции, поднять заново — состояние читается с диска без потерь.

**Снимок состояния рядом с ограниченным ожиданием.** Неблокирующий статус стоит рядом с
блокирующим `wait` (ограниченный, возобновляемый таймаут, потолок ниже клиентского). *Почему:*
без `wait` вызывающие либо крутят неограниченный опрос, либо изобретают неопровержимые «ещё
работает»; клиентский транспортный таймаут вне контроля инструмента оборвёт наивно длинный
`wait` раньше срока. *Проверка:* повторные вызовы `wait` на долгой задаче честно возвращаются
по таймауту и возобновляются.

## Безопасность мутаций

**Read-only по умолчанию, мутации наперечёт.** Число мутирующих путей на весь тул-сет —
маленькое, перечислимое, явно названное в описании каждого. *Почему:* аудитор должен ответить
«что может измениться на диске» за одно чтение короткого списка. *Проверка:* пересчитать
мутирующие пути по описаниям — число совпадает с задокументированным.

**Provenance + allowlist для инструмента записи.** Write в общее хранилище несёт allowlist
целей, обязательную запись автора/времени, опциональный read-only режим для менее доверенного
вызывающего. *Почему:* незащищённый write-путь — канал, по которому менее доверенный контент
становится каноном, который основной агент читает без сомнений. *Проверка:* запись вне
allowlist отклоняется именованной ошибкой; каждая запись несёт автора/время.

**Read-only режим для менее доверенного контура.** Флаг переключает сервер в режим, где ЛЮБОЙ
мутирующий тул отказывает независимо от аргументов. *Почему:* внешний контур должен физически
не иметь возможности мутировать состояние, а не полагаться на «не станет». *Проверка:* с
флагом — отказ на корректных аргументах; без флага — тот же вызов проходит.

## Одна реализация

**CLI поверх тех же обработчиков.** Точка входа CLI построена на тех же функциях, что
MCP-инструменты — вторая реализация не заводится. *Почему:* гарантирует одинаковое поведение
независимо от того, кто ведёт, и вдвое сокращает поверхность поддержки. *Проверка:* один
сценарий через MCP и через CLI даёт идентичный результат.

## Жизненный цикл и устаревание

**Рождение сервера = три записи одним коммитом.** Регистрация в клиентском конфиге + запись
в гейте живости — в ТОМ ЖЕ коммите, что и сам сервер. *Почему:* повторяющийся паттерн —
инструмент неделями простаивал незарегистрированным в гейте живости. *Проверка:* диф коммита
рождения содержит все три части разом.

**Баннер устаревания на процессе, не на данных.** Сервер хэширует свои исходники/конфиг при
старте, перепроверяет на каждом вызове, помечает свои ответы устаревшими при расхождении.
*Почему:* класс «правим код сервера, продолжаем говорить со старым процессом» породил серию
инцидентов «я всё починил, но ничего не изменилось». *Проверка:* поменять исходник, не
перезапуская процесс, — следующий ответ несёт признак устаревания.

**NEEDS-RESTART / MCP-DEAD в отчётах.** Агент, не способный перезапустить сервер сам, обязан
явно заявить это после дешёвого живого пинга, а не молчаливо считать код свежим. Новый ключ в
общем конфигурационном контракте требует рестарта долгоживущего процесса, даже если файл на
диске уже обновлён. *Почему:* превращает скрытую ловушку («файл обновлён» ≠ «процесс это
видит») в видимый сигнал. *Проверка:* журнал хода работ несёт явную строку эскалации там, где
код сервера менялся в рамках сессии.

## Достоверность находок и гейтов

**Guard от инцидента тестируется на точке входа инцидента.** Регрессионный guard идёт через
ТОЧКУ ВХОДА, которой воспользовался инцидент, а не через похожую CLI-обёртку. *Почему:* guard
на удобной обёртке оставляет настоящую дыру открытой, выглядя закрытым. *Проверка:*
репродукция инцидента через ЕГО СОБСТВЕННЫЙ вход после фикса даёт безопасный результат.

**«Всё живо» называет своё покрытие.** Итоговая строка гейта здоровья явно указывает «N из M»,
а не голое «всё здорово». *Почему:* ложный зелёный по умолчанию хуже честного красного — он
вводит в заблуждение активно. *Проверка:* добавить компонент, не внести его в список целей
гейта — итог обязан упасть или явно занизить счётчик.

**Серьёзность — из реального использования, в обе стороны.** Находка проверяется по тому, как
путь реально вызывался в истории — proof-of-concept может понизить приоритет (форма ни разу не
встретилась) или поднять другой (косметический на вид дефект — триггер потери данных).
*Почему:* PoC доказывает механизм, не срочность относительно остального бэклога. *Проверка:*
посмотреть реальные вызовы пути за период, не только гипотетику.

**Секреты никогда не рендерятся инструментами.** Только булев факт «настроен», никогда
значение. *Почему:* эхнутый секрет в health/диагностическом ответе попадает в лог/историю,
откуда сложно вычистить постфактум. *Проверка:* ответ с настоящим секретом в конфиге не
содержит его значения ни в одном поле.
