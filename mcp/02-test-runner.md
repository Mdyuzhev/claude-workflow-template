# 02 — Test Runner MCP (test-mcp)

Спецификация MCP-обёртки над существующей E2E/юнит-тестовой инфраструктурой проекта — не
код, контракт для построения эквивалента на своём стеке.

## Проблема

Ручной прогон полного набора тестов идёт десятки минут. Агент, запустивший его синхронно в
своём процессе, либо блокирует свой ход на всё это время, либо теряет процесс вместе со
своей сессией, если чат оборвался раньше. Дальше — классический отказ «прогон идёт»:
утверждение, которое нечем опровергнуть, если раннер не пишет на диск ничего, на что можно
посмотреть независимо. И наконец лог, разобранный глазами или собственной regexp, врёт —
две независимо написанные регулярки одного формата рано или поздно разойдутся, и вопрос
«какая права» станет спором, а не фактом.

## Поверхность инструментов

Девять тулов, разделённых на три группы.

**Запуск и наблюдение.**
- `run` — стартует детач-процесс, возвращает идентификатор запуска немедленно.
- `status` — неблокирующий снимок: фаза, прогресс, признак «лог не растёт», который сам по
  себе прогон НЕ останавливает.
- `wait` — блокирующее ожидание с ограниченным таймаутом, возобновляемое повторным вызовом с
  тем же идентификатором; не блокирует остальной сервер (параллельный `wait` по другому
  идентификатору отвечает как обычно).
- `result` — структурированный результат через единственный канонический парсер: сводка по
  умолчанию, детализация по кейсам — опционально.
- `cancel` — отмена: сначала дерево процессов конкретного запуска, широкий fallback по имени
  образа — только явно помеченным следующим шагом, если первый не добил всё.

**Реестр и история.**
- `list` — реестр тестовых файлов + отчёт о рассинхроне регистрации между несколькими
  конфигами раннера, если их несколько.
- `history` / `compare` / `baseline` — см. раздел ниже.

**Параметры `run` (в словах).** Режим — полный набор / именованное семейство спеков /
grep-фильтр / один-несколько файлов по явному пути; рабочее дерево кода — какой checkout
или `git worktree` исполнять (по умолчанию — собственное дерево сервера; полный прогон без
явно указанного дерева требует отдельного подтверждающего флага «да, я действительно имею
в виду прогон против дерева сервера», см. «Тестируемое дерево» ниже); платформа, если проект
кросс-платформенный; небольшой allowlist дополнительных переменных окружения; флаг «не
пересобирать перед прогоном»; предпросмотр без запуска (`dry_run`); режим окна — фон по
умолчанию, видимое окно — опционально. Параметр повторов сверх нуля, если нижележащий
раннер их не умеет, честно отклоняется как неподдерживаемый, а не тихо игнорируется.

## Каталог запуска (модель хранения)

Один запуск = один каталог: файл метаданных (тестируемое дерево, головной коммит, ветка,
признак «дерево грязное»), файл лога (первая строка которого — тестируемый головной коммит),
файл-сентинел завершения/провала. Это и есть источник истины о состоянии запуска, независимо
от того, жив ли ещё MCP-канал, который его запустил.

## Единый парсер

Ровно одна функция разбирает формат лога/отчёта раннера; каждый инструмент, которому нужны
эти цифры (включая сравнение и историю), вызывает именно её. Собственной regexp по сырому
логу нигде в наборе нет by design.

## Banner handshake

Каждый успешный ответ несёт первым ключом строку рукопожатия: версия сервера, короткий
идентификатор коммита процесса сервера, число ключей контракта мок-окружения (см. ниже),
тестируемый головной коммит (для тулов, которые его измеряют; `n/a` для тех, что нет).
Дешёвая проверка «сервер точно перечитал свежий код» — если исходники сервера правились, а
идентификатор коммита в баннере старый, сервер не перезапущен.

## Тестируемое дерево — не путать с запрошенным

Ответ `run` (и каждая запись истории) всегда несёт живой git-снимок дерева, которое РЕАЛЬНО
было исполнено, независимо от того, какое значение параметра рабочего дерева было передано
на входе. Известная ловушка: терминальный смок-прогон без указанного рабочего дерева и без
подтверждающего флага молча измерил дерево сервера вместо предполагаемого дерева ветки —
находка вскрылась только на приёмке. Полный прогон без явно указанного рабочего дерева ОБЯЗАН
требовать отдельного подтверждающего флага именно для этого случая — иначе тихая подмена цели
прогона проезжает дальше по конвейеру незамеченной.

## Overlap warning

Перед стартом раннер сканирует состояние других активных запусков и возвращает список
пересекающихся идентификаторов, если найдены (общий тестовый стенд/порт/окно). Это
предупреждение, не блок — прогон стартует в любом случае, решение за вызывающим.

## История, сравнение, бейзлайны

`history` читает локальный индекс завершённых прогонов и отвечает долей прохождений спека за
последние N прогонов — **но только когда решающих наблюдений (green/red, без skip/inc)
набирается не меньше пяти**; при меньшем числе — явный вердикт «недостаточно наблюдений», а
не число, посчитанное на слишком маленькой выборке.

`compare` сравнивает два прогона по статусу каждого спека, встретившегося хотя бы в одном:
- **NEW_RED** — стал red, не будучи red в прогоне сравнения.
- **LOST_GREEN** — был green, стал не-green-и-не-red (skip/inc/пропал).
- **FIXED** — был red, стал green.
- **NEW_SKIP** — не был skip, стал skip.

`baseline` записывает/читает именованную ссылку на прогон (по умолчанию «main») — то, с чем
`compare` сравнивает, если второй прогон не передан явно.

## Хранение прогонов и удержание

Правило удержания истории обязано перечислить ВСЕ легитимные места, где прогон мог
исполняться (основной checkout, связанные рабочие копии/worktree), а не только дефолтное —
иначе защита от очистки слепа к большинству реального трафика. Практический набор правил:
последние N по времени, упомянутые в бейзлайнах, сейчас активные, недавно провалившиеся
(младше порога), и упомянутые в закоммиченных доказательствах эпика/аудита (run id
встречается в трекнутых markdown/txt/log файлах). Перед реальной чисткой — режим
предпросмотра, использующий ТУ ЖЕ функцию принятия решения, что и реальная чистка, byte for
byte, а не вторую, отдельно дрейфующую копию правила.

## Удалённые/иноплатформенные маршруты (опционально)

Если часть тестов исполняется не локально (удалённый стенд, другая ОС), раннер может
маршрутизировать запуск туда по параметру, оставаясь тем же контрактом ответа (каталог
запуска, банер, парсер) — маршрут не меняет форму результата, которую видит вызывающий.

## Чего инструмент не делает

Не собирает и не деплоит продукт, не делает kill/wipe-операции на удалённой тестовой
инфраструктуре, не парсит лог сам вне единственного канонического парсера, не заменяет
собой PR-гейты, не судит о флаки по одному прогону (см. правило n≥5 выше). Всё, что вне
периметра, возвращается отдельным полем ответа, а не молчаливо опускается.

## Контракт mock-окружения

Переменные окружения для мок-серверов (внешние зависимости тестов — брокер сообщений, база
данных и т.п.) объявлены в ЕДИНОМ месте, all-or-none: если набор объявленных ключей в одном
модуле разошёлся с таблицей значений в другом, сборщик окружения бросает ошибку вместо
частичного запуска. Новый ключ, добавленный в одном коммите, требует рестарта долгоживущего
процесса раннера — код, строящий таблицу значений из модуля контракта, был импортирован один
раз при старте; «файл на диске уже содержит ключ» не то же самое, что «работающий процесс это
видит». До рестарта — прогонять тот же обработчик в свежем процессе (например, через CLI-точку
входа сервера, см. [01-design-rules.md](01-design-rules.md) § «Одна реализация»).
