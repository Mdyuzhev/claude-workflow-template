# 04 — KB MCP (база знаний)

Посекционный поиск по markdown-базе знаний: искать дёшево по теме, затем точно забрать
полное тело найденной секции — вместо того чтобы агент каждый раз перечитывал целые
документы в контекст.

## Когда использовать

Когда агенту нужно свериться с накопленным знанием проекта (инвариант, урок, решение), а не
выводить его заново. Также — живая карта модулей кода: разбирается заново при каждом
вызове, а не кэшируется, сознательно, чтобы сама карта не протухала.

## Когда не использовать

- Как источник правды для того, что меняется на каждый коммит (исходный код) — карта кода
  существует именно потому, что индексация самого кода протухала бы мгновенно.
- Как слой семантического/векторного поиска. Такой слой был построен, измерен на дюжине
  проверочных вопросов и удалён: он не ответил ни на один вопрос, на который не отвечал
  обычный полнотекстовый (BM25) поиск. Переоткрывать вопрос только с зафиксированными
  цифрами сравнения на руках, не из интуиции.

## Состав корпуса — один источник

Список документов, входящих в индекс (явные пути и/или glob-паттерны), объявлен РОВНО в
одном файле исходников сервера. Любое расширение состава (новый каталог, новый класс
документов) — осознанная правка этого файла, а не побочный эффект структуры репозитория.
WHY: неявный, выводимый на лету состав корпуса невозможно ни аудировать, ни зафиксировать
как «что именно проиндексировано на момент такого-то прогона».

## Модель хранения

- Единый файл базы данных (SQLite) — фактический источник истины для курируемых секций.
- Полнотекстовый индекс (BM25) построен над секциями документов, не над файлами целиком —
  единица поиска и единица возврата — секция.
- Файл БД коммитится в систему контроля версий, рядом с ним держится текстовый (SQL) дамп —
  специально для того, чтобы существовал диффуемый, читаемый бэкап отдельно от бинарного
  файла.

## Поверхность инструментов (шесть)

| Инструмент | Что делает |
|---|---|
| outline | Дешёвое обнаружение структуры: список документов, или заголовки секций одного документа — без тел. |
| search | Полнотекстовый ранжированный поиск: сниппеты и локации (документ + якорь секции), без полных тел. Шаг 1 двухшагового поиска. |
| get | Полное тело одной найденной секции по её локации. Шаг 2. |
| put | Запись/замена полного тела секции с пометкой «курируемое переопределение» — защищено от последующей автоматической пересборки. |
| reindex | Пересборка индекса из исходников; см. режимы ниже. |
| map | Карта модулей кода — разбирается заново на каждый вызов (см. «когда использовать»). |

## Паттерн инверсии

Крупные секции живут ПОЛНЫМ телом только в базе; исходный markdown-документ на диске
намеренно урезан до тизера (одна-две строки сути) + указателя на локацию в KB. Кто хочет
полный текст — идёт через `get` по указателю, а не читает урезанный файл и не считает его
полным. WHY: без этого правила крупные документы дублируются в двух местах, которые
расходятся при первой же правке в одном из них.

## Режимы пересборки — merge vs seed

- **merge** — единственный режим для живой базы с курируемым контентом. Пересобирает из
  исходников, СОХРАНЯЯ каждое ранее записанное курируемое переопределение.
- **seed** — деструктивный полный rebuild. Зарезервирован для одноразовой фазы начальной
  загрузки, ДО того как в базе появился курируемый контент. Запуск seed позже стирает этот
  контент.

Деструктивный rebuild и безопасный merge никогда не должны быть одним и тем же дефолтом
после того, как в хранилище появился ручной/обогащённый контент.

**Прецедент.** Долгоживущий процесс сервера, не перечитавший собственную конфигурацию «какие
документы существуют», выполнил merge-пересборку и удалил заметное количество курируемых
вручную секций документов, о которых он ещё не знал — потому что на тот момент защита от
протухания опиралась на прокси-сигнал (форму набора документов: сколько их и какие), а не на
факт устаревания собственного загруженного кода/конфига процесса.

## Guard от протухания — на чём он должен стоять

Guard обязан срабатывать на «мой собственный исходный код/конфиг изменился с момента
старта процесса», а не на косвенный сигнал вроде «форма набора документов изменилась».
Второе даёт ложные срабатывания на любое обычное легитимное добавление документа (учит
операторов обходить guard стороной) и одновременно пропускает реально протухший процесс,
у которого форма набора документов случайно не поменялась.

Guard тестируется на ДВА случая: тот, который он должен заблокировать (протухший процесс
пытается слить), и тот, который он должен пропустить (свежий процесс сливает после того, как
набор документов легитимно вырос). Гейт, доказанный только на первом случае, может «лечить»
инцидент тем, что начинает отказывать постоянно.

## Запись — allowlist, provenance, read-only режим

`put` — единственный мутирующий инструмент во всей поверхности. Для него:

- **allowlist точных целей** — какие документы вообще разрешено переопределять записью;
  попытка записать за пределами списка отклоняется с названием отклонённого ключа.
- **provenance на каждой записи** — кто/когда записал (поля автора и времени), не только
  само содержимое.
- **режим «только чтение»** — переключатель, полностью отключающий `put` и `reindex`, для
  вызывающего с меньшим доверием (второй, менее контролируемый контур наравне с основным).

WHY: инструмент записи, доступный менее доверенному вызывающему наравне с основным, — канал,
по которым менее доверенный контент становится каноном, который основной агент потом читает
без вопросов. Смягчение — allowlist + provenance + опциональный read-only, а не полагание на
то, что менее доверенный вызывающий «просто не будет» злоупотреблять доступом.

## Блокировка при записи

Запись идёт под явной блокировкой файла БД, с checkpoint журнала предзаписи (WAL) сразу
после коммита. WHY: без явного checkpoint журнал предзаписи может расти неограниченно между
пересборками и разойтись с основным файлом БД, который потом коммитится в git.

## Тесты

Собственный юнит-набор на форматирование секций, режимы reindex, allowlist записи и guard
устаревания — включая позитивный контроль guard'а (см. выше: тестируется и блокирующий, и
пропускающий случай). См. также [docs/10](../docs/10-gates-and-evidence.md) о позитивном контроле как
общем требовании к любому гейту.
