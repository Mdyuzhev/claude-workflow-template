# MCP-инструментарий проекта

Обзор вспомогательных MCP-серверов, которые проект заводит под свой цикл работы агента с
кодовой базой, и порядок чтения остальных файлов этой папки.

## Зачем проекту свои MCP-серверы

Агент, работающий циклами «рекон → правка → гейт → отчёт», раз за разом повторяет одни и
те же процедуры: прогнать тесты и разобрать лог, свериться с чек-листом закрытия задачи,
собрать документ из контента, найти прошлое решение в базе знаний, провести долгую сессию
другого агента без присмотра, сообщить владельцу о ключевом моменте. Каждая процедура,
реализуемая заново вручную или каждым агентом с нуля, обрастает своим парсером, своим
чек-листом «на глаз», своей копией логики сравнения — и копии расходятся.

MCP-сервер превращает процедуру в инструмент с ОДНИМ парсером и ОДНИМ реестром на весь
проект — отвечает фактом, который можно перепроверить, а не мнением агента. Плюс:

- **Выживание смерти агента.** Долгая операция идёт в отдельном процессе с состоянием на
  диске — гибель сессии не убивает саму операцию.
- **Машиночитаемый результат.** Ответ — структура, не сырой лог для разбора глазами/своей
  регуляркой.
- **Экономию контекста.** Инструмент по умолчанию отдаёт сводку, не вывод в десятки тысяч
  строк — цена платится один раз внутри инструмента.

## Набор инструментов

| Сервер | Задача | Мутирует? | Когда использовать |
|---|---|---|---|
| Тестовый раннер (test-mcp) | Прогон тестов детач-процессом + структурированный результат + история/сравнение | Спавнит/убивает локальные процессы, чистит свою историю прогонов | Прогон без блокировки сессии; сравнить два прогона; доля прохождений спека |
| Конвейер закрытия (close-mcp) | Чек-лист закрытия единицы работы как машинно-проверяемые пункты | Два поимённых пути: свой отчёт + опциональный reindex базы знаний | В момент закрытия — согласованность реестров/версий/тегов с фактом слияния |
| База знаний (kb-mcp) | Посекционный полнотекстовый поиск по markdown-корпусу | Один инструмент записи, помечающий секцию курируемой | Свериться с накопленным знанием вместо вывода с нуля; карта модулей кода |
| Конвейер документов (doc-mcp) | Поэтапная сборка офисного документа + PDF из структурированного контента | Запись в корень контента и в один путь доставки | По требованию, когда нужно произвести документ — НЕ поэпизодная зависимость |
| Драйвер агента (agent-driver MCP) | Запуск/наблюдение/остановка headless-сессии внешнего CLI + интроспекция истории | Спавнит/убивает процессы; не открывает credential-файлы управляемого CLI | Вести долгую сессию другого агента без присмотра, узнать что было, не карауля лог |
| Авто-возобновление (hook) | Плагин агента (не MCP-сервер), переотправляющий инструкцию застрявшей сессии | Впрыскивает ввод в живую сессию по таймеру/событию | Долгие сессии без человека, где иначе нужны ручные «подтолкни дальше» |
| Мост уведомлений (notify bridge) | HTTP-эндпоинт «уведомить владельца» в закрытом наборе моментов | Исходящий HTTP в канал сообщений | Старт/вопрос/остановка/завершение автономного прогона |
| Инфра-MCP | Наблюдение и точечное управление хост-инфраструктурой | По политике хоста — read-heavy, мутации поимённые | Диагностика инфраструктуры без прямого shell-доступа агента |

## Жизненный цикл сервера

Рождение сервера — один коммит, несущий три вещи разом: сам сервер, его строку в
клиентском конфиге MCP и его запись в гейте живости (см.
[docs/10](../docs/10-gates-and-evidence.md)). «Зарегистрируем позже» — устойчивый
анти-паттерн: инструмент выкатывается и неделями простаивает не связанным ни с чем, что
могло бы заметить его смерть.

Версия каждого сервера — собственный литерал, отдельный от версии продукта/монорепозитория:
тулинг версионируется по своему графику, а не подшивается к продуктовому релизу только
потому, что живёт в том же репозитории. Тег на релиз инструмента — свой, отдельный от тегов
продукта.

Долгоживущий процесс рано или поздно будет исполнять устаревший код: правка файлов сервера в
РАБОТАЮЩЕМ процессе не подхватывается без рестарта MCP-клиента. Отсюда два сигнала, которые
агент обязан написать в отчёте, если не уверен в свежести кода сервера, — `NEEDS-RESTART:
<сервер>` (нужен рестарт, агент сам его выполнить не может) и `MCP-DEAD: <сервер>` (сервер
недоступен вовсе) — оба после дешёвой живой проверки, не как молчаливое предположение.
Опционально сервер сам хэширует исходники при старте и помечает свои ответы устаревшими при
расхождении (подробнее — [01-design-rules.md](01-design-rules.md)).

## Позиция по безопасности

Least privilege: каждый инструмент получает ровно ту способность, которая нужна его задаче,
не более. Никаких неаутентифицированных удалённых shell-поверхностей — эндпоинт, способный
исполнить произвольную команду на хосте, требует аутентификации и сетевой границы, а не
полагается на то, что до него «никто чужой не доберётся». Секреты (токены, credentials)
никогда не живут в закоммиченном конфиге — только в локальном незакоммиченном файле на
хосте, который их использует.

## Чего в этой папке нет

Здесь нет кода: ни транспортного модуля, ни серверов, ни тестов. Это дизайн и контракт —
другая команда строит эквивалент на своём стеке по этому описанию. Конкретный стек, пути,
имена инструментов — адаптируются под проект; неизменны только принципы из
`01-design-rules.md` и форма контрактов каждого сервера.
