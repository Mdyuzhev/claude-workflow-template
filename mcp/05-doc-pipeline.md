# 05 — Doc MCP (конвейер сборки документов)

Детерминированный конвейер «структурированный корень контента → готовый офисный документ +
параллельный PDF», выставленный поэтапными инструментами вместо одного непрозрачного
скрипта «собери документ».

## Когда использовать

По требованию — когда реально нужно произвести или обновить клиентский/владельческий
документ (руководство, отчёт) из заданной структуры контента.

## Когда не использовать

- Не поэпизодная зависимость. Ноль вызовов на протяжении долгого времени — ожидаемое здоровое
  поведение такого инструмента, не признак деградации.
- Не источник скриншотов — скриншоты для документа берутся из тест-спеков продукта или
  предоставляются владельцем напрямую, никогда не автоматизацией живого рабочего стола.
- Не место для merge/tag/publish-действий над репозиторием.

## Модель хранения

Корень контента — чистые данные: структурная схема документа (главы/секции) + файлы
контента по каждой секции. Каталог доставки готовых файлов НИКОГДА не зашит в исходном коде
инструмента — это поле в том же файле данных документа, так что код вообще не обязан знать
реальный путь конкретного клиента.

## Поверхность инструментов (семь)

| Этап | Что делает |
|---|---|
| list | Read-only инвентарь: какие документы существуют, какова их структурная схема. |
| scaffold | Идемпотентное создание скелета документа. Никогда не перезаписывает непустой существующий файл. |
| check | Предсборочный структурный гейт: санитарность кодировки, запрещённые символы, негативный grep на утечки, перекрёстные ссылки плейсхолдер↔изображение. |
| build | Собирает документ. Перед записью на диск повторно прогоняет собственный гейт безопасности текста по каждой отрендеренной строке. |
| gate | Второй, независимый структурный гейт — уже над СОБРАННЫМ документом, не над исходником. |
| finalize | Доводит документ через офисное приложение (оглавление), экспортирует PDF, проверяет, что PDF не пуст и первая страница не белая, доставляет ровно два именованных файла в настроенное место — с отказом, если имя совпадает с защищённым именем файла. |
| result | Читает отчёт предыдущего этапа. «Ещё не запускался» — валидное не-ошибочное состояние, не молчание. |

## Гейты качества — что именно ловить

- **Двойное перекодирование в финальном артефакте.** Проверка на replacement-символ (типовой
  индикатор битой кодировки) слепа к классу «текст прошёл кодировку → назад → снова вперёд»:
  результат — читаемые, но неверные символы кириллицы/спецсимволов без единого
  replacement-символа. Гейт финального артефакта должен ловить именно сигнатуру двойного
  перекодирования, а не только присутствие replacement-символа.
- Счётчики страниц/иллюстраций документа — сверяются с ожидаемым планом, не просто
  «файл непустой».
- Устаревший заголовок/версия в теле документа — отдельная проверка, независимая от факта
  успешной сборки: сборка может пройти чисто и всё равно нести устаревший заголовок,
  унаследованный из шаблона прошлой версии.

## Внешние зависимости — мягкий, а не жёсткий отказ

Внешние рантайм-предусловия (библиотеки сборки/разбора документа, изображений, PDF, само
офисное приложение) проверяются по факту использования, с подсказкой по установке при
отсутствии — а не являются жёсткими зависимостями, ломающими старт сервера. `finalize`
перечисляет ВСЕ отсутствующие предусловия разом, а не падает на первом найденном.
Незадекларированная амбиентная зависимость (присутствующая на машине случайно, не по
декларации) может исчезнуть незаметно после обычной переустановки зависимостей — декларируй
явно каждую внешнюю библиотеку/приложение, от которого зависит хотя бы один этап.

Каждый внешний спавн процесса — синхронный и ограничен по времени, никогда не долгоживущий.
Осиротевший инстанс офисного приложения (если автоматизация зависла) обнаруживается снимком
процессов до/после и принудительно чистится в гарантированном блоке очистки — не только на
счастливом пути.

## Отказы и liveness

Реально воспроизводимый класс краха: паттерн проверки на запрещённые символы может подвесить
однопоточный процесс катастрофическим бэктрекингом регулярного выражения на специально (или
случайно) сконструированном входе — общий принцип ограничения времени исполнения
пользовательских паттернов см. в [01-design-rules.md](01-design-rules.md).

Инструмент «по требованию» нуждается в собственной пробе живости именно потому, что «ноль
вызовов» — ожидаемое поведение и само по себе не доказывает, что инструмент ещё работает.
Пробу гоняют на каждом плановом housekeeping, не дожидаясь следующего реального заказа.

## Тесты

Собственный юнит-набор на каждый этап конвейера и на оба гейта (пред- и постсборочный),
включая позитивный контроль на детекторе двойного перекодирования (заведомо испорченный
образец должен красниться, чистый — зеленеть).
