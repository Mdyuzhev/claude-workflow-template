# 03 — Close Conveyor MCP (close-mcp)

Спецификация MCP-обёртки над чек-листом закрытия единицы работы (эпика/задачи) — не код,
контракт для построения эквивалента на своём стеке.

## Назначение

Ловит класс дефекта «налог на согласование», проявляющийся месяцы спустя: строка реестра,
отставшая от факта слияния, протухший маркер дрейфа, каталог задачи, не переехавший в
архив. Инструмент ловит этот класс ИМЕННО в момент закрытия, читая тот же машиночитаемый
реестр пунктов, которому обязан удовлетворять каждый закрываемый эпик, вместо того чтобы
человек сверял чек-лист глазами.

## Чек-лист как машинный реестр

Человекочитаемый чек-лист «что проверить перед закрытием» (канонические формулировки — см.
[docs/08](../docs/08-housekeeping-and-pre-flight.md)) одновременно существует как машинный
реестр: id, заголовок, категория (`scope`: всем эпикам / только продуктовым сборкам / только
линии периодического обслуживания / только внешнему интегратору) и режим проверки (`auto` —
полностью автоматический; `evidence` — требует приложенных доказательств; `hybrid` —
смешанный). Документ — источник ФОРМУЛИРОВОК; реестр — источник МАШИННОГО номера и
категории того же пункта; документ не дублирует номера, а отсылает к живому реестру — иначе
вручную поддерживаемая вторая копия тихо расходится с кодом при смене формулировки/состава.

Типичный состав пунктов (обобщённо): реестры merged-состояния vs факт слияния; поддельные
маркеры дрейфа; синхронный бамп версии по обязательным источникам + файлам блокировки
зависимостей; тег на коммите слияния; свежесть установочных артефактов; перенос задач в
архив; обязательные файлы рабочего пакета; извлечённый урок + ротация архива; кодировка +
база знаний; оставленные рабочие копии и отбившиеся ветки; заявленная дисковая чистка/
перенос файлов доказана, не продекларирована; живость служебных процессов; регрессия
базового аудита кода; отчёт владельцу ровно одним огороженным блоком; «нулевое
прикосновение» к продуктовой зоне, если скоуп это требует.

## Модель вердикта

Каждый пункт возвращает РОВНО один из четырёх статусов, никогда голое булево значение:

| Статус | Значение | Причина |
|---|---|---|
| **PASS** | условие выполнено | — |
| **FAIL** | условие НЕ выполнено — любой FAIL блокирует закрытие | — |
| **N-A** | неприменим для класса эпика | начинается с «неприменимо:» + класс/прецедент |
| **INC** | применим, вердикт не получен в этом прогоне | «доказательство отсутствует:»/«не выполнено:»; блокер |

Общая функция-валидатор бросает исключение при любом нарушении формы (неизвестный статус,
неверный префикс причины, доказательства не в виде массива) — вызывается на каждом вердикте
ПЕРЕД тем, как что-либо вернуть или записать. Голый pass/fail схлопывает «неприменимо» и
«недостаточно данных» в тот же сигнал, что провал или успех, стирая разницу между
заблокированной и чистой проверкой.

## Класс эпика — из git-диффа, не из декларации

Класс закрываемого изменения («документация» / «продуктовая сборка» / «инструментарий»)
ВЫВОДИТСЯ из git-диффа известных «источников версии» между базой и головой — никогда не
передаётся флагом вручную. Ноль затронутых источников → «документация» (пункты
версии/тега/changelog → N-A с прецедентом). Согласованное подмножество одной категории →
тот класс обязателен. Частично согласованное подмножество (часть тронута, часть — нет) →
настоящий FAIL «согласованность версии нарушена», не проглатывается молча — вызывающий не
может неверно задекларировать тип изменения.

## Разрешение базы сравнения

Построение контекста НИКОГДА не угадывает молча — порядок: явно переданная база; если
голова — коммит слияния (два родителя), берётся первый родитель; общий предок головы и
удалённой основной ветки, только если он отличается от головы; если ничего не применимо
(голова уже равна удалённой основной ветке — состояние сразу после push), контекст
помечается «база не резолвится», классификатор не запускается, КАЖДЫЙ пункт → INC — а не
молча читает пустой дифф как «документация, всё неприменимо».

## Поверхность инструментов

- `list` — реестр чек-листа целиком (id/заголовок/область/режим). Никогда не мутирует.
- `run` — исполняет применимые пункты в диапазоне «до/после», пишет файл отчёта (см.
  «Мутирующие пути» ниже); неприменимые пункты — N-A-строки, не выпадают молча.
- `check` — одна проверка по id, без записи отчёта; именованная ошибка на неизвестном id.
- `result` — чтение последнего записанного отчёта.
- `kb` (доменно-специфичный) — probe/reindex базы знаний: read-only по умолчанию, мутирующий
  путь один — жёстко прописанная безопасная команда СЛИЯНИЯ, никогда полная пересборка.
- `report_lint` — линтер формата отчёта владельцу против строгого формата обрамления (см.
  [docs/10](../docs/10-gates-and-evidence.md) § «Формат отчёта»).

Отдельный CLI вызывает ТЕ ЖЕ обработчики — прогонять close-проверки без живого MCP-канала
(см. [01-design-rules.md](01-design-rules.md) § «Одна реализация»).

## Мутирующие пути — ровно два, оба поимённые

1. **Запись собственного итогового отчёта** — включена по умолчанию для «прогнать и
   записать», но НИКОГДА не создаёт директорию единицы работы сама (опечатка в имени
   проваливается громко — предупреждением без записи файла); если ветка эпика кодирует ИНОЙ
   идентификатор, чем переданное имя каталога, запись подавляется без явного флага
   «разрешить чужое имя» — не давая параллельному контуру записать отчёт в чужой каталог.
2. **Опциональная переиндексация базы знаний** — строго режимом слияния (никогда «с нуля»,
   стирающим вручную обогащённые секции); тест проверяет побайтово команду слияния.

Всё остальное — read-only инспекция git-истории и файловой системы; инструмент никогда не
`merge`/`tag`/`push`, и не решает философски, что значит «готово», сверх того, что может
доказать из истории и диска.

## LIVE-пункты, известные красные, гейты close-цикла

Пункты с живым сетевым вызовом (внешний брокер, удалённый сервис) ретраятся один раз перед
тем, как засчитать FAIL — единичный сетевой сбой не блокирует закрытие. Известные
преэкзистентные провалы — в отдельном allowlist с указанной причиной: allowlist виден,
причина зафиксирована, не спрятана. Набор гейтов, обязательных перед закрытием, ВЫЧИСЛЯЕТСЯ
из того же реестра гейтов, что проверяет мета-гейт целостности (см.
[docs/10](../docs/10-gates-and-evidence.md)) фильтром по полю «когда обязателен» (`close` vs
более редкое `ship`) — не отдельным текстовым списком, который может разойтись с реальным
набором.

## Как FINAL использует конвейер

Финальная фаза эпика (см. [docs/11](../docs/11-acceptance-and-final.md)) прогоняет `run` на
слитом дереве ПОСЛЕ терминального прогона тестов и ДО отчёта владельцу — любой FAIL/INC
блокирует переход к отчёту; отчёт с необъяснённым INC не считается зелёным.

## Типичные находки конвейера

Реестры, отставшие от факта слияния; отсутствующий бриф/отчёт рабочего пакета;
отсутствующий или неаннотированный тег на коммите слияния; грязное рабочее дерево на момент
закрытия; устаревшие транскрипты (гейт перегонялся до того, как в измеряемую зону попали
последние правки — включая сами журналы хода работ).
