# kit/RULES.md — канон правил внешнего участника

Каждое правило — с кратким «почему» (какой класс дефекта оно закрывает). Это
канон: `AGENTS.md` и `CONTRIBUTING.md` (корневые копии из `kit/templates/`)
на него ссылаются, а не дублируют текст.

> hint: замени плейсхолдеры `<typecheck-cmd>`/`<unit-cmd>`/`<e2e-spec-cmd>`/
> `<build-wrapper>`/`<artifacts-dir>`/`<notify-client-cmd>`/
> `<release-zone-paths>` на реальные команды/пути, удали этот блок.

## 1. Ветка и модель PR

Работа — в отдельной ветке от свежего `main`, одна ветка — одна тема. Прямой
push в `main` закрыт — изменения попадают только через PR с приёмкой; merge
выполняет только владелец репозитория после ревью.

Пока PR живёт, `main` уходит вперёд. Подтягивай его сам (`git merge
origin/main`) и **сам разрешай конфликты у себя** — до приёмки: PR приходит
на ревью уже мержабельным, а решение по каждому конфликту (что взято, что
отброшено, почему) описывается в PR.

## 2. Сборка — только обёртками проекта

Сборка приложения — **только** через обёрточные скрипты проекта
(`<build-wrapper>` и аналоги). Прямой вызов нижележащего инструмента сборки
запрещён — обход обёртки теряет проверки окружения и даёт несовместимые
флаги сборки.

## 3. Гейты перед PR

Перед открытием PR прогнать локально минимум: `<typecheck-cmd>` (0 ошибок),
`<unit-cmd>` (зелёный прогон), и если менялись/добавлялись end-to-end тесты —
точечный прогон затронутого сценария (`<e2e-spec-cmd>`), именно обёрткой
проекта: она задаёт адреса моков, пересобирает артефакт и чистит состояние
приложения перед прогоном (подробности и запасной путь — `kit/STAND.md`).
Полный smoke по всем сценариям локально не требуется — он идёт отдельным
релизным конвейером.

**Если PR не касается кода приложения** (инструменты, скрипты, документация)
— гейты выше неприменимы: помечай `N/A` с причиной, приводи взамен проверки
по типу вклада (синтаксическая проверка, поведенческий прогон с фактическим
выводом, grep-подтверждение). Неприменимость гейта меняет **форму**
доказательства, не отменяет его: PR без единой проверки не принимается.

**Предпочтительный путь прогона для агента — MCP-инструмент test-mcp** (см.
`kit/TEST-RUNNER.md`): переживает смерть агента/сессии, даёт машиночитаемый
итог из единственного парсера логов репозитория. Голый вызов обёртки в
синхронном вызове shell — fallback с причиной в PR. Для человека без
MCP-клиента путь остаётся рекомендацией, не блокером.

## 4. Тестовые контракты — только добавлять

Существующие тестовые идентификаторы и тестовые контракты не переименовывать
и не удалять — только добавлять новые. Переписывание контракта — отдельное
согласование с ревьюером до реализации.

## 5. Новые зависимости — с обоснованием

Новая зависимость добавляется только с явным обоснованием в описании PR:
зачем нужна, почему нет альтернативы среди уже использующихся пакетов.

## 6. Инфраструктурные зоны

**Релизный контур — без согласования не трогать:** `<release-zone-paths>`
(инструменты релиза, CI-конфиг, файл версии, changelog, версии в манифестах) —
ведёт отдельный внутренний процесс, правка извне рассинхронизирует его молча.

**Внутренний рабочий контур команды — по умолчанию не трогать:** случайная
правка почти всегда ошибка адресации; осмысленный вклад (новый скилл,
доработка внутренней документации) — обычным PR с обоснованием, решение за
владельцем на ревью.

**Артефакты PR-цикла — в `<artifacts-dir>/<эпик>/<участник>/`**, не в
собственных каталогах верхнего уровня.

**Параллельные линии разработки** — резервации номеров задач/тестовых
идентификаторов и швы коллизий между одновременно растущими линиями →
`kit/PARALLEL-LINES.md`.

## 7. Конвенции UI проекта

> hint: замени на список принятых UI-конвенций проекта (единый компонент для
> иконок вместо построчных вставок, дизайн-токены вместо literal-значений,
> единый слой состояния вместо локального per-компонента). Источник —
> дизайн-система проекта; здесь — только ссылка, не копия.

## 8. Жёсткий предел на генераторы и насосы данных в тестах

Любой генератор или насос данных внутри теста (цикл записи, поток байт,
повторяющаяся отправка) обязан иметь жёсткий верхний предел — по байтам, по
числу итераций или по таймауту. Unbounded-цикл в тесте — блокер ревью: такие
циклы роняли хост, на котором гонялся тест.

## 9. DoD — зелёный прогон с текстовым выводом

Критерий готовности — зелёный прогон команды с сохранённым текстовым выводом
(что выполнено, сколько тестов прошло/упало), а не «код написан». Прогоны
прикладываются в PR текстом — числа и итог, не пересказ.

**Тест под баг обязан быть показан красным до фикса.** Зелёный прогон
доказывает, что код работает, но не что тест ловит именно эту поломку — тест
может проходить и на сломанном коде. Регрессионный тест прикладывается
двумя прогонами: на коде без правки (падение с текстом ассерта) и с правкой
(зелёный); для собираемых приложений — пересобрать артефакт между прогонами,
иначе тест гоняется по старой сборке.

Два прецедентных класса ложной зелени: сценарий, задевающий путь, который и
так работал (обнаруживается только откатом правки с пересборкой); и
сценарий, бьющий в дефект, но маскируемый вышележащим независимым слоем
восстановления состояния — если у системы несколько слоёв защиты одного
состояния, тест обязан нейтрализовать верхний.

### 9.1 Форма пруфа для правки UI-поведения

- **Меняет UI-поведение, стенд доступен → end-to-end тест обязателен**
  (красным до фикса, зелёным после, с пересборкой между прогонами).
- **Стенд недоступен** (развилка — `kit/STAND.md`) **→ component-тест** той же
  нормы **плюс явная декларация в PR**; незаявленный пропуск = непрогнанный гейт.
- **Не меняет UI-поведение** (логика, парсер, формат данных) — unit-теста
  достаточно.

Компенсирующий прогон на приёмке не делает component-тест «временным».

## 10. Красный тест — диагноз перед фиксом

Красный тест не скрывается, не ослабляется подменой ассерта и не удаляется
ради зелёного прогона. Порядок: сначала диагноз с доказательством причины,
затем точечный фикс — не бездумный повторный прогон в надежде на флейк.

## 11. Дисциплина веток и рабочих каталогов

Рабочее дерево — разделяемый ресурс: переключение веток под ногами чужой
активной работы обесценивает проверяемое (артефакт расходится с исходниками,
тесты измеряют чужой код).

**(a)** Один каталог — один владелец: чужой `checkout`/`switch`/`reset` в
нём запрещён, включая «на минутку». **(b)** Параллельная работа — только
через `git worktree add`/`remove`/`prune`. **(c)** Pre-flight каждого
запуска — сверить текущую ветку с ожидаемой; расхождение = **СТОП + доклад**.
**(d)** Финишное состояние — своя ветка либо снятый worktree; «оставил на
`main`» недопустимо. **(e)** Останов посреди операции — всегда СТОП-доклад с
описанием состояния; брошенный `merge`/`rebase` без доклада — инцидент.

## 12. MCP-серверы и инструменты, вкладываемые в репозиторий

Согласованный вклад-инструмент (MCP-сервер, CLI-утилита) обязан соответствовать
шести правилам — полный текст и код-пруфы → `mcp/01-design-rules.md`: (а)
graceful degradation — протокольный цикл стартует всегда, отсутствие
конфига даёт внятную ошибку инструмента, не падение до старта; (б) пути
только через безопасное URL→path преобразование, корректное на Windows;
(в) сетевые вызовы — с таймаутом; (г) честный симметричный dry-run — превью
тем же кодом, что реальная отправка; (д) `.gitignore`-миграции — с
compat-строками; (е) тесты мутирующих вызовов — точное сравнение URL целиком.

## 13. Отбивки владельцу — обязательны

Владелец узнаёт о ключевых моментах работы из канала уведомлений, а не из
опроса агента. Вызов `<notify-client-cmd>` обязателен в четыре момента (канон
и полный текст → `mcp/07-notify-bridge.md`): `start` (задача взята, окружение
развёрнуто, до первого коммита), `question` (СТОП-на-вопросе), `halt`
(аварийный останов), `close` (push сделан, PR готов).

Три следствия: **доставка без отбивки не завершена** (отчёт заявляет
готовность только после вызова, результирующая строка вложена в отчёт/PR как
есть); **отбивка шлётся в момент события, не постфактум**; **отбивка
никогда не гейтит** — never-fatal; «недоставлено» при недоступном канале
валидно, пропуск самого вызова — нет.

Механизация `start`: `kit/templates/progress.md`, Entry 0 = дословная
результирующая строка вызова `start`, пишется ДО первого кодового коммита
задачи. Задача без Entry 0 не начата.

## 14. Точность отчёта и артефактов доказательств

**(а)** Артефакт, названный в отчёте/PR, обязан существовать в ветке —
доказательство только листинг коммитированных файлов, не рабочая копия;
имена совпадают побуквенно. **(б)** Транскрипт снимается с HEAD отдаваемой
ветки — задевающий его коммит требует перегона и коммита свежего.
**(в)** Текстовые артефакты — UTF-8 без BOM + LF, проверка командой, не
глазами: окончания строк (ни одного CRLF), первые байты не сигнатура BOM,
скан на битую кодировку — успех (платформенные редиректы молча пишут другую
кодировку, визуальный просмотр этого не видит).
**(г)** Каждое утверждение PR-описания сверяется с репозиторием перед
отправкой — «Отложено» не содержит уже сделанную этим же PR работу, «не
менялось» доказывается диффом, пункт из «Отложено» не исчезает молча.
**(д)** Числа гейтов — полными словами честной тройкой (`N passed / M failed
/ K skipped`), без однобуквенной нотации. **(е)** Шапка тестового файла
обновляется тем же коммитом, что меняет тесты — дыры в нумерации объясняются
строкой в шапке, не молчанием.

## 15. Задача-цепочка эпиков

Если задача выдана как цепочка внутренних эпиков, агент проходит ВСЮ цепочку
сам, без остановок на подтверждение между звеньями. Полная механика, роли,
сентинелы, RESUME-канон, контекстная диета и раунды приёмки →
`docs/12-external-contours-and-chains.md`; шаблоны для самой работы →
`kit/templates/chain-brief.md`, `card.md`, `progress.md`, `decisions.md`.

Короткий канон: отдельная ветка и PR на каждое звено (не мержатся, служат
контрольной точкой); по завершении — ОДИН кумулятивный PR, звеньевые
закрываются как superseded. «Автономно» = «без вопросов между звеньями», не
«одним непрерывным прогоном»: `progress.md` — дописываемый журнал (Entry 0 =
отбивка `start`), упавшая сессия продолжается с того же места. По-звеньевой
отчёт — не остановка; внешних остановок ровно две — аварийный останов и
открытый кумулятивный PR. После потери контекста — перечитать ТЕКУЩИЙ бриф,
не журнал (его старые записи о завершении superseded новым брифом).
Close-набор гейтов — вывод из реестра, не список из брифа. Замороженное
число несёт команду, которой получено. Два одинаковых провала подряд — стоп
и замер держателя ресурса. Спорные решения — консервативный дефолт + запись
в `decisions.md`; `question` — только для необратимых развилок. Незавершённое
звено — отложенный пункт с причиной в кумулятивном PR, не остановка. Байтовая
гигиена (§14в) — на каждый новый транскрипт цепочки.
