# PR With Proofs — оформить PR с доказательствами

> hint: подставь реальные названия разделов своего PR-шаблона вместо ссылок
> на `kit/PR-TEMPLATE.md`, если шаблон называется иначе. Структура (вывод, а
> не пересказ → self-review → self-acceptance → зависимости отдельным
> разделом) переносится без изменений.

## 1. Структура описания

Заполняй PR по `kit/PR-TEMPLATE.md` целиком, без пропущенных разделов.
Пустой раздел — это не «нечего добавить», а сигнал, что ты его не заполнил:
если раздел неприменим (например, «Новые зависимости»), пиши явно «нет», а
не удаляй раздел.

## 2. Прогоны — вывод, не пересказ

Каждый гейт из `kit/skills/implement-and-gates/SKILL.md` — в PR как текст
вывода команды, а не как утверждение:
- плохо: «тесты прошли»;
- хорошо: `<команда прогона>` → `Tests: 318 passed`, код завершения 0.

Так же для статической проверки (число ошибок) и для точечного end-to-end
прогона, если менял сценарий (число прошедших/упавших; канон обёртки вместо
голого вызова раннера — `kit/RULES.md` §3). Вывод — то, что реально
напечатала команда, не переформулировка своими словами.

## 3. Каждое заявленное поведение — с командой проверки

Если в описании PR утверждается «теперь X работает» — рядом должна быть
команда, которой ревьюер может это перепроверить сам (запрос, конкретный
тест, шаг в интерфейсе). Утверждение без способа проверки для ревьюера — не
доказательство, а обещание.

Каждая команда, публикуемая в PR или README, прогнана буквальным copy-paste
из финального текста — не по памяти и не «эквивалентным» вариантом: битый
пример в README ломает setup-путь каждому следующему читателю. И каждый
файл, на который ссылается код, README или описание PR, либо присутствует
в diff/репозитории, либо ссылка снимается: цитата без первоисточника
лишает ревьюера возможности сверить рационале.

## 4. Отступления и известные ограничения — самовскрытием

Если по ходу задачи план из `kit/skills/take-task/SKILL.md` пришлось
изменить, или в решении осталось известное ограничение (что-то работает не
полностью, покрыто не всеми случаями) — напиши об этом сам, до того как это
найдёт ревью. Сюда же — непрогнанный гейт с причиной: недоступный стенд,
версия рантайма, отличная от референсной (канон обоих случаев —
`kit/STAND.md`).

Находки, вскрывшие причину глубже тикета, или смежные дефекты, найденные по
дороге и намеренно не тронутые, идут не сюда, а в свой раздел PR-шаблона —
«Находки глубже тикета» (`kit/PR-TEMPLATE.md`, канон — `take-task` §4a).
Самовскрытое ограничение — рабочий момент. То же самое, найденное
ревьюером в описании, которое его не упоминает, — подрыв доверия к
остальным утверждениям PR.

## 4a. Публикуешь артефакты — скрабь и проверяй по коммиту

Логи прогонов, verification-файлы и замеры, прикладываемые к PR, коммитятся
в каталог, отведённый под артефакты вклада (`kit/RULES.md` §6) —
собственные каталоги верхнего уровня репозитория не создаются (канон —
`kit/RULES.md` §6).

Перед публикацией — PII-скраб паттернами (чек-лист «Чистота публикации» в
`kit/PR-TEMPLATE.md`): имена пользователей ОС, домашние пути, hostnames,
IP-адреса, внутренние идентификаторы заменяются синтетикой или
плейсхолдерами вида `<os-user>`, `<stand-host>`.

Три ловушки, каждая — из реального ревью:

- **Проверяй то, что вошло в коммит, а не рабочую копию.** Скан по рабочей
  копии ничего не говорит о коммите: файл мог вовсе не попасть в
  скраб-коммит. Сверка — статус скраб-коммита и поиск по git-блобам.
- **Логи на Windows сверяй по содержимому коммита, не рабочей копии.**
  Автоматическая конвертация переносов строк на checkout меняет байты —
  байт-точная сверка и парсеры логов на рабочей копии ломаются, хотя в
  репозитории файл корректен.
- **История ветки помнит нескрабленное.** Скраб последним коммитом не
  удаляет ранние версии из истории — обычный merge пронесёт их в основную
  ветку навсегда. Если такие версии в истории есть — заяви это в PR явно;
  решение (squash / переписать историю / принять как есть) — за владельцем.

## 4b. Self-review таблица — перед открытием PR

До открытия PR проходит пруф-ревер: каждое утверждение описания сверяется
с конкретным артефактом в коммите. Ревьюер не должен ловить разрыв между
«текстом PR» и «содержимым коммита» — это работа автора.

**Таблица (вставляется в PR в раздел «Self-review»)** — три обязательные
колонки:

| Утверждение PR | Артефакт пруфа (commit:path) | Сверка |

- **Утверждение PR** — конкретный факт («добавлено поле X», «гейт Y
  зелёный», «уведомление о закрытии отправлено»).
- **Артефакт пруфа** — путь в коммите + хеш, например
  `<hash>@path/to/file.ts:53` или `commit <hash> raw/run.log`.
- **Сверка** — `OK` / `mismatch` / `N/A — <причина>`. Пустых строк быть не
  может: если утверждение нечем сверить, оно не должно быть в PR.

Отдельная строка для уведомления о закрытии, если проект использует такой
мост (`kit/RULES.md` §13): утверждается «уведомление отправлено», артефакт —
результирующая строка из вывода клиента, сверка `OK` только если она
действительно напечатана.

**Гейт-таблица — то же самое для прогонов**: каждое заявленное число
проходит через содержимое коммита и сверяется с тем, что в PR. На Windows —
обязательно по содержимому коммита, не по рабочей копии (ловушка §4a).

(Мост уведомления, который считался отправленным, но не был, — реальный
класс провала; отсюда self-review таблица делает такое видимым до открытия
PR, а не постфактум.)

_Шаблон таблицы — `kit/PR-TEMPLATE.md` (раздел «Self-review»)._

## 4c. Self-acceptance pass — перед link PR

Перед link PR (контрольная точка в цепочке эпиков, `kit/RULES.md` §15) или
перед закрытием одиночной задачи автор проводит self-acceptance pass:
проходит по всем пунктам контракта/ТЗ и пруфам, как это сделал бы ревьюер,
и фиксирует вердикт по каждому.

**Self-acceptance — не полноценный многоролевой аудит.** Это разные
процедуры: аудит смотрит на готовый код несколькими независимыми линзами;
self-acceptance — авторская сверка «заявил → доказал» перед открытием PR.
Они не заменяют друг друга.

**Минимальный состав self-acceptance pass:**

1. Каждый пункт контракта/ТЗ — статус `DONE`/`PARTIAL`/`N/A` + пруф
   (commit:path).
2. Каждый гейт — зелёный или `N/A` с причиной + вывод команды (полный
   текст, не пересказ).
3. Каждое утверждение PR — сверено по self-review таблице (§4b).
4. Уведомление о закрытии отправлено, если проект его использует
   (`kit/RULES.md` §13) — результирующая строка в PR.
5. `progress.md` — последний Entry описывает текущее состояние точно:
   номер/дата/commit-hash/state/next-step присутствуют, не противоречат
   коду.

Self-acceptance pass не отменяет ревью владельца — он снимает с рельсов
тривиальные возвращения («не прикреплён лог», «утверждение без пруфа») и
даёт владельцу начать с содержательных замечаний.

_Шаблон self-acceptance — `kit/PR-TEMPLATE.md` (раздел «Self-acceptance»)._

## 5. Новые зависимости — отдельный явный раздел

Любая новая зависимость — отдельным разделом в PR с обоснованием: зачем
нужна, какую альтернативу без новой зависимости рассматривал и почему
отклонил. Если зависимостей не добавлял — раздел всё равно есть, с текстом
«нет». Без согласования в PR-описании новые зависимости добавлять нельзя
(канон — `kit/RULES.md` §5).

## 6. После ревью

Замечания ревью правь в той же ветке — не открывай новый PR и не создавай
новую ветку под те же правки. После каждой правки по замечаниям — повтори
актуальные гейты из `kit/skills/implement-and-gates/SKILL.md` и обнови
вывод в описании, если он изменился.

**Повторная ревизия — обновляй и само описание PR, не только прогоны.**
Если между заходами изменилось поведение (сняли флаг, поменяли эндпоинт,
переписали контракт команды) — описание, оставшееся от первой ревизии,
документирует то, чего в коде уже нет: ревьюер сверяет код с неверным
эталоном и тратит заход на несуществующее расхождение. По каждому
замечанию ревью в новой ревизии пиши, чем именно оно закрыто (файл и что
там теперь) и как это проверить.

**Переименовал команду/контракт — перечитай окружающую прозу.**
Токен-замена по всем вхождениям сама по себе документ не чинит: абзацы
вокруг продолжают описывать старое поведение, и читатель по ним
реинтродьюсит ровно тот баг, который правка чинила. README или док,
противоречащий коду того же PR, — возврат на доработку.

Merge в основную ветку выполняет только владелец репозитория после
одобрения (канон — `kit/RULES.md` §1). Сам себе PR не мержишь и не
форсируешь ветку.
