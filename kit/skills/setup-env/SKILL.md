# Setup Env — развернуть окружение

> hint: подставь реальные названия зон/команд своего проекта вместо общих
> формулировок ниже. Структура (клон → зависимости → сборка обёртками →
> стенд → smoke → MCP-живость) переносится без изменений.

## 1. Клон и ветка

1. Склонируй репозиторий.
2. Обнови основную ветку.
3. Создай ветку от свежей основной: `feat/<короткое-имя>` (канон —
   `kit/RULES.md` §1). Одна ветка — одна тема — не смешивай в ней
   несвязанные правки.
4. Периодически подтягивай основную ветку в свою по ходу работы.

## 2. Зависимости

Проект может держать несколько независимых зон со своим набором
зависимостей (например: приложение и его end-to-end обвязка) — ставь
зависимости в КАЖДОЙ зоне отдельно, командой, закреплённой lock-файлом этой
зоны, а не общей командой на весь репозиторий.

Версия рантайма (язык/платформа) зафиксирована в `kit/STAND.md` — гоняешь
на другой версии, декларируй это явно в PR.

Проверь, что всё встало, ДО первой правки: базовая статическая проверка
проекта (type-check/lint) должна отработать без ошибок инфраструктуры —
не про твой код, про то, что окружение живое.

## 3. Сборка — только обёртками

Приложение **никогда** не собирается вызовом нижележащего инструментария
платформы напрямую (сборщика/компилятора/упаковщика в обход скриптов
репозитория). Все сборки — только через обёртки репозитория (см. манифест
сборки в корне зоны). Прямой вызов нижележащего инструмента пропускает
шаги подготовки окружения (проверки, конфиг для тестовой изоляции) и даёт
артефакт, который не соответствует тому, что реально тестируется.

Побочный эффект некоторых сборочных операций — регенерация файлов, которые
при этом трекаются в репозитории (сгенерированные схемы, лок-файлы и т.п.).
Перед коммитом проверь статус рабочего дерева — случайно регенерированные
файлы не коммить, откатывай их.

## 4. Собственный мок-стенд

Если приложение обращается во внешние сервисы — для разработки и
end-to-end тестов нужен собственный локальный мок-стенд, не боевые сервисы
и не чужая инфраструктура.

Полный рецепт — от чистой машины до зелёной smoke-проверки — пошагово в
`kit/STAND.md`. Не дублируй его здесь: разверни стенд по инструкции оттуда.

## 5. Smoke-проверка стенда — ДО первой строчки кода

Не начинай писать код, пока стенд не подтверждён живым. Пройди
smoke-проверки из `kit/STAND.md` — свой набор на каждый путь развилки
(выданный стенд или локальный) — и убедись, что отвечают все моки. Стенд,
поднятый наполовину, даёт ложные красные тесты позже — их придётся
диагностировать заново, теряя время на то, что проверяется за секунды
сейчас.

**Если стенд не отвечает** — не считай это тупиком и не переключайся молча
на другой путь: порядок действий (повторить smoke → запросить у владельца
стенда запасной адрес → согласовать с ревьюером компенсирующие пруфы и
записать это в PR) описан в `kit/STAND.md`, раздел «Выданный стенд не
отвечает». Правка, которой стенд не нужен вообще (чистая логика, закрываемая
статическими/юнит-проверками), этим не блокируется.

Только после зелёной smoke-проверки стенда — либо согласованного решения
по предыдущему абзацу — переходи к MCP-живости (§6), затем к
`kit/skills/implement-and-gates/SKILL.md`.

## 6. MCP-инструменты — обязательно для агента

Если в проекте есть MCP-сервер, гоняющий гейты (runner MCP —
`kit/TEST-RUNNER.md`), агент гоняет гейты предпочтительно через него, а не
голыми синхронными командами: голый прогон в синхронном шаге блокирует
агентскую сессию на десятки минут и теряет процесс при смерти сессии;
runner MCP переживает смерть агента/сессии (detached-процесс + маркер на
диске) и даёт машиночитаемый итог из единственного парсера логов
репозитория.

Для человека без MCP-клиента обёртки репозитория остаются рабочим путём —
MCP рекомендован, но не блокер.

**Живость MCP проверяется на старте сессии** (для агентов с MCP-клиентом):
ping-образный вызов (список инструментов/спеков) отвечает осмысленно, без
таймаута/ошибки протокола.

**В `progress.md` пишется строка `mcp:`** в Entry 0:

- для агента с живым MCP: `mcp: <server> alive (<ping-вызов> OK, N <единиц>)`;
- для сессии без MCP-клиента в текущем контексте: честная причина
  (`mcp: unavailable(<причина>) — gates run via direct commands with
  transcripts committed`).

Запись `mcp:` не для красоты — она отличает «MCP был, но не позвал» от
«MCP не был доступен, гейты пошли через fallback». Без этой строки ревьюер
не может разобрать, почему в задаче нет транскриптов прогона через MCP.

Канон — `kit/RULES.md` §12 (MCP-серверы и инструменты) + `kit/TEST-RUNNER.md`
(инструменты и параметры).
