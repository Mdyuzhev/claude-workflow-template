# Implement & Gates — сделать и прогнать гейты

> hint: замени порядок гейтов в §6 на реальные команды своего проекта.
> Структура (одна тема на ветку → малые шаги → правило красного теста →
> гейты по порядку → текстовый вывод) переносится без изменений.

## 1. Одна ветка — одна тема

Не смешивай в одной ветке несвязанные правки. Если по ходу работы находишь
проблему за пределами своей задачи — фиксируй её отдельно (issue или
заметка владельцу), не тяни в текущий PR.

## 2. Малые шаги, прогон после каждого

Разбивай задачу на маленькие изменения из своего плана (3–5 шагов из
`kit/skills/take-task/SKILL.md`). После каждого шага — прогони тесты зоны,
которую тронул. Не копи untested-изменения на несколько файлов сразу — если
тесты покраснели, проще понять, от какого именно шага, когда шаг один.

## 3. Правило красного теста

Красный тест — сигнал, не помеха:
- **не скрывай** — не оборачивай в отключение теста/try-catch, глотающий
  ошибку;
- **не ослабляй** — не меняй ассерт под фактический (неверный) результат;
- **не удаляй** существующий тест, чтобы обойти красноту;
- сначала диагноз (почему падает — конкретная причина, не гипотеза), потом
  фикс. Правь причину, а не симптом.

Если красный тест был таким уже на основной ветке до твоей — не выдавай его
за свой, но и не выключай: сообщи владельцу репозитория и оставь его как
есть, задокументировав в PR-описании.

## 4. Жёсткий предел на генераторы данных в тестах

Любой генератор или насос данных внутри теста (цикл, наполняющий коллекцию,
поток байт, повторные запросы) — только с явным верхним пределом: конкретное
число, конкретный таймаут. Unbounded-цикл в тесте — блокер ревью без
исключений: такой тест способен исчерпать память или зависнуть на реальной
машине, а не только локально у автора.

## 5. Тестовые контракты — только добавлять

Тестовые идентификаторы и другие тестовые контракты (селекторы, атрибуты, на
которые опираются существующие тесты) — переименовывать и удалять нельзя.
Новые — добавляй свободно. Изменение существующего контракта — отдельное
согласование с владельцем репозитория (`kit/RULES.md` §4), не молчаливая
правка внутри задачи.

## 6. Гейты перед PR — по порядку

Прогони строго в этом порядке, каждый следующий — только если предыдущий
зелёный:

1. Статическая проверка (type-check/lint) — ожидаемый результат: **0
   ошибок**.
2. Юнит/component-тесты — ожидаемый результат: **все тесты зелёные**.
3. Если менял или добавлял end-to-end сценарий: точечный прогон затронутого
   сценария через обёртку репозитория (не полный набор и не голый вызов
   нижележащего раннера) — обёртка задаёт адреса моков, пересобирает
   артефакт и чистит состояние приложения (канон — `kit/RULES.md` §3,
   запасной вариант вызова — `kit/STAND.md`).

**Меняешь пользовательское поведение — форма пруфа задана политикой, а не
выбирается по вкусу:** при доступном стенде end-to-end сценарий обязателен,
при недоступном — component-тест плюс явная декларация в PR (канон со всеми
случаями — `kit/RULES.md` §9; что делать с неотвечающим стендом —
`kit/STAND.md`).

Не открывай PR, если хотя бы один гейт красный. Если гейт падает по причине,
не связанной с твоей правкой (флейк, окружение) — не игнорируй молча:
перезапусти один раз, задокументируй в PR, если повторилось.

Гейты выше адресованы основному коду приложения. Вклад вне его (инструменты,
скрипты, документация, скиллы) закрывается проверками другого вида —
перечень и правило выбора — `kit/RULES.md` §3.

## 7. Сохраняй вывод гейтов как текст

Для каждого прогона сохраняй консольный вывод текстом (число тестов, число
упавших, код завершения) — он пойдёт в PR-описание как доказательство, не
пересказ. Скриншот или фраза «тесты прошли» доказательством не считаются —
только текст команды и её вывод.

## 8. Дальше

Когда все гейты зелёные и вывод сохранён — переходи к
`kit/skills/pr-with-proofs/SKILL.md`.
