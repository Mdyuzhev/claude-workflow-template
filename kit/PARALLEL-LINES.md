# kit/PARALLEL-LINES.md — параллельные линии разработки

> hint: заполняй этот файл только если в проекте реально две и более линии
> разработки растут из одной точки одновременно (своя команда + внешняя
> параллельная линия). Если линия одна — оставь только §1 с одной строкой
> «резерваций пока нет» и удали остальное. Удали этот блок после заполнения.

Канон резерваций и швов для линий, растущих из одной точки одновременно.
Контракт существует, чтобы merge любой из них был дешёвым — обе стороны
знают заранее, какое пространство имён их, а какое чужое, и в каком месте
кода придётся столкнуться независимо от резерваций.

**Своя линия не трогает чужую до её собственного сигнала** — если задача
касается зоны другой линии вне того, что описано в этом файле, это не твоя
задача, пока владелец той линии явно не передаст её сюда.

## 1. Резервации

| Пространство | Линия A | Линия B |
|---|---|---|
| Номера эпиков/задач | `<PRJ-1xx>` | `<PRJ-2xx>` |
| Номера тестовых сценариев (общий реестр) | `<диапазон>` | `<диапазон>` |
| Префикс тестовых идентификаторов | `<prefix-a->` | `<prefix-b->` |
| Литерал типа сущности | `<'kind-a'>` | `<'kind-b'>` |
| Префикс команд ядра/бэкенда | `<prefix_a_>` | `<prefix_b_>` |
| Модуль состояния (рекомендация) | `<aStore>` | `<bStore>` |
| Переменные окружения мок-стенда | новый ключ — только через владельца общего набора | новый ключ своей линии — отдельным пунктом здесь |

Дописывай столбец на каждую новую параллельную линию по мере появления;
удаляй строку только если пространство перестало существовать (не
переиспользуется).

### Ловушка: префикс уже занят другим механизмом

Прежде чем резервировать префикс тестового идентификатора для новой линии —
проверь грепом по всему репозиторию, что он не занят существующим,
несвязанным механизмом (частый случай: короткий префикс совпадает буквами
с существующей, не имеющей отношения к новой линии фичей). Коллизия
байт-в-байт с существующими тестами — блокер, не мелочь.

## 2. Швы гарантированных коллизий

Каждый шов — место, где обе линии физически правят один и тот же файл.
Правило одно для всех: **ADDITIVE-only** — добавлять новый case/запись в
конец, никогда не трогать существующие ветки. Кто вторым доходит до merge —
тот ребейзится и чинит конфликт шва на своей стороне (см. §5).

| Шов | Расположение | Форма правки |
|---|---|---|
| Единственная точка регистрации хендлеров | `<файл>` | Новые записи — единым блоком в конец списка |
| switch/case по виду сущности (несколько копий) | `<файлы, каждый со своим switch>` | Новый case в КАЖДОМ месте; список мест не централизован — держи его актуальным здесь |
| Union-тип вида сущности | `<файл:поле>` | Optional-поле; неизвестное значение падает в безопасный дефолт, не крашит |
| Меню создания новой сущности | `<файлы с hardcoded списком пунктов меню>` | Новая запись в каждый список меню — забытый пункт делает фичу физически недостижимой из интерфейса, даже если она полностью работает под капотом (см. `docs/11-acceptance-and-final.md`) |
| Реестр тестовых сценариев (несколько копий-конфигов) | `<файлы>` | Новая строка в конце ВСЕХ копий, в одинаковом порядке; номера сценариев — устойчивые идентификаторы, не позиции массива |

### Чек-лист: новый ключ конфигурации — одним коммитом

Новый all-or-none ключ (переменная окружения мок-стенда, ключ реестра) —
во всех местах, где перечисляется полный список, одним коммитом: источник
правды состава + документ (`kit/STAND.md`) + все файлы окружений, если
проект их использует. Частичное обновление списка — конфигурационный
дрейф, который всплывает только когда кто-то использует ключ, забытый в
одном из мест.

### Чек-лист: новое пользовательское текстовое поле

Новое поле, которое пользователь вводит и которое затем сохраняется/
экспортируется/логируется — проверь ВСЕ места, через которые оно течёт:
форма ввода → модель сохранения → экспорт в сторонний формат → маскирование
в логе, если поле может нести секрет. Пропуск одного звена — самый частый
класс регрессии на новых полях.

### Чек-лист: интеграционный PR шва — аудит удалённых строк

Когда линия B мержит PR, трогающий общий шов, — недостаточно проверить, что
её собственные добавления на месте. Отдельно проверь diff на предмет
УДАЛЁННЫХ строк, принадлежащих линии A (случайное затирание чужой ветки
switch при неаккуратном ручном разрешении конфликта) — сравни итоговый файл
с последней известной версией линии A построчно, не полагайся на то, что
git разрешил конфликт «чисто».

### Чек-лист: паритет исполнителя сценариев для новой сущности

Если у проекта есть отдельный «раннер» сохранённых сценариев, который
исполняет вид сущности иначе, чем прямая интерактивная отправка, — новая
линия обязана проверить, что раннер умеет её новый вид, а не только прямой
путь. Расхождение раннер/прямой путь — известный класс дефекта: находить
его — успех приёмки, прятать — провал.
