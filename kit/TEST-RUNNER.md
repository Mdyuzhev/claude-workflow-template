# kit/TEST-RUNNER.md — прогон end-to-end через runner MCP

> hint: замени имена инструментов/параметров на состав своего MCP-сервера;
> структура разделов (зачем, подключение, режимы, история, banner,
> restart-протокол, пределы) переносится без изменений. Канон дизайна —
> `mcp/02-test-runner.md`. Удали этот блок после заполнения.

## Зачем он нужен

Ручной прогон end-to-end ломается в нескольких местах, и MCP-обёртка их
закрывает.

**Прогон не переживает ход агента.** Полный прогон идёт десятки минут.
Агент, запустивший его синхронно, либо блокирует свой ход, либо теряет
процесс вместе со своей сессией. Запуск через MCP порождает detached-процесс,
который живёт независимо и сам ставит на диск маркер завершения — прогон
переживает и смерть агента, и рестарт самого MCP-сервера. Состояние лежит в
каталоге запуска на диске, а не в памяти сервера.

**«Прогон идёт» — утверждение, которое нечем опровергнуть.** Классический
отказ: ждун сидит на файле, которого раннер никогда не пишет, и часами
честно докладывает «ещё работает». Проверка статуса смотрит на РОСТ лога, а
не на финальную строку, и отдаёт фазу, прогресс и признак «лог не растёт»,
который сам по себе прогон не убивает. Блокирующее ожидание строится на том
же читателе — с честным дедлайном, вместо ручного цикла poll+sleep.

**Лог, разобранный глазами или своей регулярным выражением, врёт.** В
репозитории должен быть ровно один парсер логов прогона. Инструмент
получения результата вызывает именно его и отдаёт структуру: сводка, тесты,
тайминги, плоский список падений. Собственной regexp по сырому логу в
инструменте нет by design — своя расходится с проектным гейтом, и PR
отклонят по расхождению цифр.

**«Этот тест и вчера был красным, или это я его сломал?» — раньше требовало
памяти человека.** История/сравнение/бейзлайн читают локальный индекс
завершённых прогонов и отвечают на это структурно: доля прохождений
сценария за последние N прогонов, дифф двух прогонов по категориям
исправлено/впервые сломано/впервые пропущено/регресс, именованный бейзлайн
для дефолтного сравнения.

## Подключение

Инструменту не нужны внешние зависимости сверх среды исполнения самого
MCP-сервера. Регистрация — обычная запись stdio-сервера в конфиге
MCP-клиента, путь — абсолютный.

> **Ловушка дрейфа пути.** Если путь к серверу в конфиге указывает на
> отдельный рабочий каталог (worktree), а не на основной checkout, — после
> удаления этого каталога путь становится невалидным, и сервер молча
> перестаёт стартовать в следующей сессии. Фикс — раз и навсегда указывать
> путь к ОСНОВНОМУ checkout'у; параметр рабочего дерева на самом вызове
> прогона (см. «Worktree-прогоны» ниже) позволяет исполнять прогон против
> любого рабочего каталога, оставаясь подключённым через стабильный путь.

Живая проверка без клиента — минимальный JSON-RPC handshake (`initialize` +
`tools/list`) через stdin/stdout процесса сервера.

## Моки: внешнему участнику — только `local`

Внешний участник использует режим локального стенда (`kit/STAND.md`, путь
B) — режим, адресующий инфраструктуру владельца, внешнему участнику
недоступен и не нужен.

## Фон по умолчанию — окно прогона не появляется вообще

Прогоны по умолчанию исполняются в фоновом режиме окна — приложение под
тестом не всплывает поверх остальных окон и не крадёт фокус. Отчёт,
упоминающий прогон в процессе или только что завершённый, несёт строку
«как посмотреть» — путь к логу плюс команда для отслеживания хвоста; это
чинит репорт вида «не вижу никаких тестов» — фоновый режим невидим
человеку, смотрящему на экран, хотя сам прогон реален. Владельческий смок,
который владелец будет смотреть глазами, использует видимый режим окна.

## Worktree-прогоны и «тестируемое дерево»

Прогон принимает параметр рабочего дерева — исполняется против указанного
рабочего каталога, а не обязательно против того дерева, от которого
запущен сам сервер. Ответ прогона всегда несёт «тестируемое дерево»
(коммит, который реально тестировался) отдельно от того, что было
запрошено — не путай их: расхождение между «запрошено» и «реально
исполнено» само по себе полезный сигнал, а не шум.

Полный прогон без явного рабочего дерева требует отдельного явного
подтверждающего поля («да, я действительно имею в виду прогон против
дерева сервера») — защита от случайного полного прогона не того, что
думал вызывающий.

## Прицельные прогоны

Один файл, именованное подмножество («семья»), список файлов по пути —
вместо полного набора. Параметр повторов сверх нуля честно отклоняется как
неподдерживаемый нижележащим раннером, а не тихо игнорируется.

## История, сравнение, бейзлайны

Локальный append-only индекс завершённых прогонов плюс отдельный небольшой
файл именованных бейзлайнов. Порог минимального числа наблюдений — прежде
чем доверять доле прохождений как метрике, а не шуму одного прогона.

## Хранение прогонов и авто-чистка

Один запуск = один каталог (статус, лог, маркер завершения/провала).
Ретенция — последние N прогонов + недавние падения + прогоны, на которые
ссылается именованный бейзлайн; режим предпросмотра очистки без реального
удаления перед тем, как чистить по-настоящему.

## Banner-строка рукопожатия

Каждый успешный ответ несёт первым ключом строку версии/короткого коммита
сервера/числа ключей контракта моков/тестируемого дерева — дешёвая проверка
«сервер точно перечитал свежий код». Если версия в баннере не совпадает с
ожидаемой после правки самого инструмента — сервер не перезапущен (см.
следующий раздел).

## NEEDS-RESTART / MCP-DEAD

Канон рестарта серверного процесса, живущего от основного checkout'а, —
`kit/STAND.md`, раздел «MCP servers». Здесь не дублируется.

## Что инструмент не делает

Не собирает и не деплоит бинарь на удалённые машины, не чистит окружение на
чужом стенде, не парсит лог сам и не запускает нижележащий раннер
напрямую — только существующие обёртки репозитория. Всё, что вне периметра
инструмента, возвращается отдельным полем ответа, чтобы «команда
сформирована» нельзя было прочитать как «окружение готово».

Два известных предела. Если сценарий в одном логе исполнялся дважды
(повтор), в разбор попадает последний блок — падения первой попытки видны
только в самом логе. И признак «лог не растёт» означает «требуется
внимание», а не «мертво» — сам по себе он прогон не останавливает,
остановить может только явная отмена.

## Гейты PR это не отменяет

Структурированный результат — удобный источник цифр для описания PR, но
приёмка остаётся прежней: гейты из `kit/skills/implement-and-gates/SKILL.md`
и их текстовый вывод в PR по канону `kit/skills/pr-with-proofs/SKILL.md`.

Канон дизайна MCP-инструментов такого рода — `mcp/02-test-runner.md`.
