# PIPELINE.md — канон рабочего цикла

> Единая точка входа в процессную модель: бриф (техлид + владелец) → **одна команда**
> оркестратору → он ведёт цикл автономно (рекон → скоуп → фитч + self-audit A–G + фолд →
> кодинг волнами → close без merge) → СТОП с отчётом → приёмка владельца → GO = оркестратор
> сам выполняет FINAL (§9.3, §10). У цикла ровно одна внешняя остановка — приёмка (§9);
> HALT-форки — условные остановки внутри цикла.
>
> Файл **не дублирует механику**: анатомия task-файлов, изоляция файлов, diag-then-fix,
> DoD = проходящий тест, smoke policy — в [WORKFLOW.md](./WORKFLOW.md) и [docs/](../docs/);
> здесь — только ссылки.

---

## §0. Роли и аллокация моделей

| Актор | Модель | Что делает |
|---|---|---|
| **Техлид** (чат) | Opus | Бриф с владельцем (§2), post-hoc verify после FINAL (§10). Не авторит файлы. |
| **Оркестратор** | Opus, единственный экземпляр в сессии | Единственный получатель команды цикла; ведёт весь цикл автономно; держит меню HALT (§9.1); раздаёт волны — [templates/orchestrator-template.md](./templates/orchestrator-template.md). |
| **Субагенты** | Sonnet по умолчанию, модель задаётся явно | Все правки — код/сборка/тесты/доки/git. Явный параметр модели на КАЖДОМ спавне (R6/R10), дефолт запрещён; отчёт волны несёт «субагенты: <модель> ×N». |

Младший уровень (Haiku) по умолчанию не используется; опциональное расщепление по классу задач
— [WORKFLOW.md §26](./WORKFLOW.md).

**Кто авторит файлы.** Всегда оркестратор через субагентов из task-файлов, включая
процессные/doc-эпики; техлид планирует и синтезирует, не редактирует. Внешний аудиторский
рой — опциональная надстройка: рекон (§3) и fitch-audit (§6) по умолчанию ведёт оркестратор.

---

## §0.5. Языковая политика

Кратко: артефакты для агентов (команды, брифы, PLAN, task-файлы, контракты, `decisions.md`,
verify-отчёты, промпты, коммиты, комментарии) — английский. Всё для человека (чат владельца,
отчёты, приёмка вкл. MANUAL-SMOKE, CHANGELOG, уведомления) — язык владельца. Старый корпус
переводится постепенно, по касанию эпиком.

## §0.6. Стартовый ритуал

`/init` перед первым действием КАЖДОЙ сессии, без исключений («продолжаю чужой контур» —
не освобождение). Каждый спавн субагента несёт явный параметр модели; дефолты
харнесса/инструмента никогда не переопределяют канон — [RULES.md R10](./RULES.md#r10-стартовый-ритуал-и-канон-модели-субагентов).

## §1. Канон цикла (единый)

```
бриф (чат: техлид + владелец, §2)
        ▼
   одна команда оркестратору
        ▼
┌────────────────────────────────────────────────────┐
│  цикл автономно: рекон(§3)→скоуп(§4)→фитч(§5)→      │
│  self-audit A–G+фолд(§6)→кодинг волнами(§7)→        │
│  close без merge(§8)                                │
└────────────────────────────────────────────────────┘
        ▼
   СТОП с отчётом (§8)
        ▼
   приёмка владельца до merge (§9.2 — ручной смок)
        ▼
   GO = оркестратор сам выполняет FINAL (§9.3→§10)
```

Промежуточных чат-гейтов нет — **ОДНА команда** покрывает путь от брифа до отчёта; переходы
между внутренними шагами держит машинный DoD, не человек.

---

## §2. Бриф

Пишет техлид с владельцем **до** старта, на диске. Обязательные части: решения владельца
(не пересматриваются); проблема/цель как факт + желаемое состояние; скоуп/вне скоупа; оси
рекона (§3); указатели-якоря БЕЗ глубокой верификации, каждый «перегреп обязателен» (глубокую
делает фактура — рекон перепроверяет с нуля); инварианты и 0-touch зоны; правило скоупа
(минимум · вместимость · куда уходит переполнение); меню HALT (§9.1, не расширяется на
ходу); измеримые критерии успеха; план verify техлида (§10); режим lean/full (§5). Шаблон —
[templates/brief.md](./templates/brief.md).

Калибровка: мелкий эпик — дефолты техлида; крупный — 3–5 вопросов до брифа. Решения
владельца — одним сообщением на «ок» перед запуском; команда запуска — закоммиченный
артефакт эпика.

---

## §3. Рекон

Рой независимых субагентов по осям брифа; **3+ согласны = firm finding**. Adversarial
verify обязателен для утверждений об отсутствии — один grep не доказывает отсутствие
(нужны grep по дереву + проверка регистраций/UI + проверка на заглушки). Re-baseline на
текущий HEAD **на каждый эпик** ([RULES.md R4](./RULES.md#r4-head-и-теги-по-loose-refs)).
Формат — [templates/recon-request.md](./templates/recon-request.md); неверный seed-якорь
флагуется явно, не переписывается молча.

**Выход** — фактура на диск; рекон **не чинит**, только фиксирует (починка — §7). Глубину
выбирает оркестратор по задаче; фактура на старом коде пересобирается с нуля; владельцу
уходят только вопросы, не документ.

---

## §4. Скоуп

Оркестратор выбирает сам, по правилу брифа. Что не влезло — явно в фактуру как вход
следующего эпика, не в текущий «раз уж мы здесь».

---

## §5. Фитч

Контракт — **пять ролей** (аналитик / дизайнер / техлид-планировщик / тестировщик /
devops), каждая своя секция или честный `not_applicable`. Контракт inline: сигнатуры и
гейты волн — **до** self-audit (§6). Выход: контракт + план + task-файлы (сигнатура + DoD;
тело пишет исполнитель). Механика — [WORKFLOW.md §6](./WORKFLOW.md). Формат (full/lite) —
по размеру, решает оркестратор.

---

## §6. Self-audit A–G + фолд

Ведёт сам оркестратор, свежий adversarial-субагент, **ДО W1**. Шаблон —
[templates/fitch-audit-prompt.md](./templates/fitch-audit-prompt.md).

| # | Направление | Что ловит |
|---|---|---|
| A | Coverage | требования покрыты задачами и QA |
| B | Feasibility | сигнатуры сверены с кодом |
| C | File isolation | один владелец на файл в волне |
| D | Waves | порядок волн, зависимости |
| E | DoD greps | false-green hunt |
| F | Invariants | инварианты не нарушены |
| G | Missing edges | пропущенные кейсы плана |

**HIGH = блокер W1** — `файл:строка` + фикс. **Фолд** — полная перезапись контракта, не
построчная правка. **Self-audit оркестратора всегда достаточен** — фиксится молча, владелец
видит итог в отчёте.

---

## §7. Кодинг волнами

W0→final автономно, без чат-остановок. Машинный DoD = самоостанов волны.

**Post-wave verify** — отдельный субагент, не самоотчёт исполнителя; вердикт по волне
выносит только он. Отчёт любого субагента разделяет VERIFIED/DISPATCHED — _см. канон:
`REFERENCE.md` § «VERIFIED vs DISPATCHED»_. Границы доверия при чтении данных —
[RULES.md R8](./RULES.md#r8-границы-доверия-инструкции-данные-секреты); надёжность гейтов —
[RULES.md R9](./RULES.md#r9-целостность-гейтов-четыре-правила).

**Diag-then-fix** для сложных красных; **self-heal ≤2** на гейт, третий — HALT (§9.1).
**HALT — только по меню §9.1.** Долгие прогоны держит только оркестратор в своём фоне.

**Отчёт волны** — один абзац с номерами гейтов. Объём тестов — по риску; полный смок
обязателен на close.

### §7.1. Матрица верификации (обязательна)

До тестов — матрица «требование × {позитив, негатив, edge}»; DoD: каждое требование во всех
трёх классах либо `not_applicable` с причиной. Артефакт —
`.claude/fitch/<epic>/test-matrix.md`, шаблон [templates/test-matrix.md](./templates/test-matrix.md).

---

## §8. Close без merge + отчёт

Оркестратор сам: доки/changelog; версия **в lockstep** по источникам продукта (см.
`CLAUDE.md`); артефакт + контрольная сумма; инсталлятор на каждом продуктовом close;
чек-лист смока приёмки 5–10 пунктов ([templates/MANUAL-SMOKE.md](./templates/MANUAL-SMOKE.md));
пикапы в ОДНУ секцию пула; архив в `done/<epic-id>/`; урок → REFERENCE; временные файлы
удалены; чистый `git status`.

**`git merge`/тег/push НЕ на close** — их делает FINAL (§10) по GO (§9.2).

**СТОП с отчётом** несёт: выбор скоупа (§4); метрики гейтов; артефакты + суммы; что не
влезло — каждая строка подкреплена командой или помечена непроверенной
([RULES.md R9](./RULES.md#r9-целостность-гейтов-четыре-правила)).

**Формат отчёта — условие завершённости.** Вне ОДНОГО fenced md-блока с оградой из ЧЕТЫРЁХ
обратных апострофов (бэктиков), или с более чем одной строкой-подводкой снаружи, — несданный отчёт: тот же
статус, что у пропущенной записи в changelog, закрывается так же — пересдать, не оспаривать.
Канон — [docs/10-gates-and-evidence.md §5](../docs/10-gates-and-evidence.md#5-формат-отчёта-владельцу-канон),
шаблон — [templates/owner-report.md](./templates/owner-report.md).

## §9. Человеческие гейты

Всё вне списка оркестратор решает и делает сам.

### §9.1. HALT-форки

Только при: новой зависимости; архитектурном сдвиге за пределами брифа; продуктовом
(поведенческом) решении; красном гейте после 2 self-heal; нарушении священного инварианта.
Меню — заранее в брифе (§2), новых категорий на ходу нет.

### §9.2. Приёмка владельца до merge

После СТОП (§8) владелец гоняет ручной смок — единственная проверка глазами перед merge, вся
сразу (не по волнам).

**«Пройти путь пользователя».** Возможность может быть полностью подключена в
модели/обработчиках, проходить весь автотест — и быть недостижимой руками, если места
интерфейса, которые её создают, не обновлены; автотест через внутреннее состояние эту зону
не видит. Защита: юнит-тест паритета + один сквозной тест по реальным кликам. Полная версия
— [docs/11-acceptance-and-final.md](../docs/11-acceptance-and-final.md).

### §9.3. FINAL — по GO, без отдельной команды

GO (§9.2) = оркестратор немедленно сам: merge, тег, push, реестры, kb-reindex, архив,
чистка диска. До GO merge не происходит — цикл стоит на СТОП. Механика — §10.

### §9.4. Уведомления владельца

Мост уведомлений — в четырёх моментах: старт (до W1), вопрос/HALT (§9.1), close/FINAL (§10).
Никогда не гейтит; отличается от четырёх-бэктикового отчёта, не заменяет его. Механика,
шаблон, урок «поле на входе ≠ поле в рендере» — [mcp/07-notify-bridge.md](../mcp/07-notify-bridge.md).

## §10. FINAL и post-hoc verify техлида

По GO (§9.3) оркестратор сам: `merge --no-ff`; тег на коммите заморозки; явный push, теги
отдельно; реестры + kb-reindex слиянием + архив в `done/<epic-id>/`; чистка диска по
актуальному списку (шаблонный список протухает); гейт кодировки + мета-гейт целостности
([RULES.md R9](./RULES.md#r9-целостность-гейтов-четыре-правила)) — зелёные на финальном
дереве; ветка удалена локально и на удалённом; отчёт — тот же формат (§8); машинный гейт
чек-листа — конвейер закрытия ([mcp/03-close-conveyor.md](../mcp/03-close-conveyor.md)).
**Набор close-гейтов печатается из реестра**, не подбирается вручную из брифа.

**Post-hoc verify техлида** (по диску): тег → фактический merge-коммит; loose-ref основной
ветки == merge-коммит, удалённое синхронизировано; источники версии сверены между собой;
mtime артефакта > последний код-коммит; числа гейтов пересчитаны тем же парсером; строка —
grep по дереву отгруженного коммита; архивация — переписью файлов; дерево чистое.
Расхождение = **HALT** + возврат оркестратору, не ручная правка. Полная механика —
[docs/11-acceptance-and-final.md](../docs/11-acceptance-and-final.md); канон гейтов —
[docs/10-gates-and-evidence.md](../docs/10-gates-and-evidence.md).

## §11. Чекпоинт-протокол

Если внешний чекпоинт-канал недоступен/не определён в репозитории — чекпоинт делается
**полной перезаписью** файла контракта состояния, не через мёртвый канал. Шаблон —
[templates/handoff.json](./templates/handoff.json). Пишется: на ключевом шаге цикла; при
сжатии контекста; в конце сессии (+ «первые шаги следующей»). Привязки «после каждой
стадии» нет — по факту прогресса. Честная проверка канала — реальная запись через него.

## §12. Цепочки эпиков (внешний контур)

**Цепочка** — многозвенный эпик, обычно внешний контур: ветка на звено, PR звена как
чекпойнт (не сливается), по завершении — один кумулятивный PR. _См. канон:
[kit/RULES.md](../kit/RULES.md) § «Задача — цепочка эпиков»_ — модель звена; журналы
`progress.md`/`decisions.md`; условие закрытия; диета контекста; канон
доказательств. Роли, мост-MCP, сентинелы `HALT:`/`AWAIT-LEAD:`/`CHAIN-DONE:`, строка
возобновления — [docs/12-external-contours-and-chains.md](../docs/12-external-contours-and-chains.md).

## §13. Поезда слияния

Несколько готовых цепочек/PR — в **поезд**: бамп версии и релизный прогон платятся один раз
на партию. Слияние по очереди («кто готов — тот первый»), lockstep-бамп = заморозка кода,
один терминальный прогон, сравнение с предыдущим (новый красный/пропуск = не чист), тег,
артефакты, реестры, только потом push. Находка владельца на артефакте — фикс на том же
поезде, тег переносится, версия не меняется повторно. Параллельные линии — резервации
идентификаторов и правило «швы только аддитивны» фиксируются контрактом заранее. Полная
механика — [docs/13-merge-trains-and-parallel-lines.md](../docs/13-merge-trains-and-parallel-lines.md).
