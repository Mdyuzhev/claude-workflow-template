# REFERENCE.md — уроки + evergreen-канон

Два разных содержимого в одном файле, не путать: (1) горстка **evergreen**-разделов — общий
канон, на который указывают другие документы, не архивируется никогда; (2) **уроки проекта** —
накопительный журнал `L-NNN-NN`, где живут только два последних эпика, старше — переезжает в
`archive/lessons-archive.md`. Файл не хранит процессы (это `WORKFLOW.md`) и не хранит состояние
очереди (это `ROADMAP.md`).

---

## 1. Canonical (evergreen — не архивировать)

### (a) Формат отчёта оркестратора владельцу — CANONICAL

Любой отчёт оркестратора владельцу на любом стопе цикла (wave-отчёт, STOP/close, приёмка,
FINAL) — **ОДИН fenced md-блок**, внешняя ограда — **четыре бэктика**, вне блока максимум одна
строка-подводка. Отчёт, сданный в другом виде, — отчёт НЕ сдан: та же весовая категория, что
пропущенная запись CHANGELOG или несобранный артефакт — пересдать, не спорить.

Требования:
- один блок на весь отчёт (несколько блоков = несколько кликов и потерянные куски между ними);
- внутри отчёта команды/вывод — в собственных тройных фенсах; внешняя четверная ограда не
  ломается о первую внутреннюю;
- заявления, которые будут проверяться (хеши, счётчики, пути, вывод git) — дословный вывод
  команды, не пересказ;
- числа гейтов — полным словом-тройкой «N passed / M failed / K skipped», никогда однобуквенной
  нотацией (прецедент-класс: сокращение было прочитано как противоположное значение).

Причина (если источник её называет; иначе — просто правило без домысленного обоснования):
отчёт часто копируется владельцем целиком в другой канал одним действием — вне блока таблицы
рассыпаются, форматированный вывод команд теряет выравнивание, доказательная часть гибнет первой
при копировании.

### (b) Evidence canon: число гейта без закоммиченного транскрипта не существует

Число, заявленное в отчёте без транскрипта, закоммиченного в измеряемую ветку (UTF-8/LF, снятого
именно с той головы, которая описывается), не существует — считается «не измерено».

- Число в ЗАГОЛОВКЕ отчёта/транскрипта — это заявление; доказательство — только вывод парсера
  поверх тела самого артефакта, воспроизведённый проверяющим. Прецедент-класс: закоммиченный
  транскрипт, чья рукописная шапка утверждала «все N PASSED», при том что тело того же файла
  показывало один провал.
- Числа выводятся скриптом поверх леджера/индекса, никогда не печатаются рукой поверх памяти
  или поверх собственного прогона.
- Замороженное число (целевой леджер, «было» для сравнения) несёт рядом команду, которой оно
  получено — число без деривации переживало несколько раундов приёмки как красивая фикция.
- Транскрипт несёт измеренное дерево: путь/worktree и хеш HEAD — прогон без этой строки на
  цепочечном гейте однажды измерил не ту голову, и каждое производное утверждение оказалось
  ложным по построению.
- Рецепт захвата транскрипта: заголовок с тестируемым HEAD и командой → таймаут → сам вывод →
  последняя строка `EXIT=<n>` с реальным кодом возврата. Захват через безопасный редирект
  оболочки; никогда через путь, эмитирующий UTF-16/BOM/CR — гигиена решается в момент захвата,
  не постфактум.
- Гейт, который не запускался, не получает транскрипт с рукописным `EXIT=0` — честная запись
  «N/A» с причиной в обычном документе.
- Артефакты, названные в отчёте, обязаны существовать в отдаваемой ветке — доказательство только
  листингом версионной системы, не рабочей копией: успешная запись на диск не делает файл
  артефактом.

### (c) Отчёт субагента различает VERIFIED и DISPATCHED

Субагент, который сам что-то запускает через дальнейших исполнителей (делегирует, а не только
исполняет), не заявляет о завершении, пока каждая делегированная единица не вернулась. Отчёт
такого субагента разделяет два списка:

- **VERIFIED** — то, что сам субагент наблюдал напрямую (прочитал файл, увидел вывод команды).
- **DISPATCHED** — то, что было запущено, но результат не был дождан/подтверждён этим же
  субагентом.

Прецедент-класс: отчёт о развёртывании назвал работу выполненной, опираясь на фоновые процессы,
которые на самом деле ещё не завершились — расхождение поймано только повторной прямой проверкой
живой системы оркестратором, а не по отчёту.

### (d) KB MERGE-дисциплина (если в проекте используется база знаний с инверсией доков)

Если крупные секции операционных доков вынесены в базу знаний (полнотекстовое хранилище +
`teaser + → см. базу` в самом `.md`), правки после инверсии применяются **только в режиме
слияния** (merge с текущим состоянием базы), никогда в режиме полной пересадки (seed), который
стирает уже обогащённые секции. Живой сервер такой базы не подхватывает правку своего же кода
без рестарта — устаревший процесс либо отказывает с явной пометкой «нужен рестарт», либо (что
опаснее) молча удаляет секции новых документов при слиянии из старого кода. Признак «эта секция
инвертирована или нет» и правило для НЕинвертированных секций (диск — источник истины, чтение
базы перед записью недостаточно) — держать одним решающим правилом в этом же разделе, не
разносить по документам.

## 2. Уроки проекта

Формат одной записи: `L-NNN-NN` (эпик-порядковый).

```
### L-NNN-NN — <короткий заголовок>
**Контекст:** <что происходило, 1-2 предложения, без project-specific деталей>
**Правило:** <что теперь делать вместо>
**Как применять:** <конкретный триггер/чеклист-пункт>
**Evidence:** <путь к артефакту/транскрипту, доказавшему урок>
```

Политика: здесь живут уроки двух последних закрытых эпиков. При закрытии третьего — самый
старый урок переезжает в `archive/lessons-archive.md` с сохранением номера (не renumber).

Пример (единственный полностью заполненный, generic, для калибровки формата):

### L-NNN-NN — Гейт без позитивного контроля не доказывает ничего

**Контекст:** гейт на проверку кодировки файлов молчал «чисто» несколько эпиков подряд; когда в
репозиторий попал файл с реально повреждённой кодировкой, гейт этого не заметил — сравнение шло
по кодовым точкам, а повреждение было на уровне сырых байт.

**Правило:** любой гейт, способный сказать «чисто», обязан в том же прогоне показать «грязно»
на фикстуре, отличающейся от чистой ровно тем дефектом, который гейт заявляет ловить. Гейт без
такого позитивного контроля не считается доказанным — только зарегистрированным с открытым
статусом.

**Как применять:** при добавлении нового гейта — первым коммитом идёт грязная фикстура и
подтверждение, что гейт на ней краснеет, вторым — сам гейт в реестре.

**Evidence:** `<path-to-positive-control-transcript>`

## 3. Специфика стека проекта

Плейсхолдер-раздел под инварианты конкретного проекта (транспортный слой, хранилище состояния,
build-дисциплина, соглашения именования модулей). Наполняется техлидом по мере роста проекта;
здесь — только ссылки на канонический дом каждого инварианта (обычно `CLAUDE.md` — короткий
список, полное объяснение — сюда).

- `<инвариант 1>` — короткое правило + `<почему>`.
- `<инвариант 2>` — …

---

*Правится оркестратором на каждом close (новый `L-NNN`) и раз в несколько эпиков ротацией §2 в
архив. `CLAUDE.md` не хранит уроки, `WORKFLOW.md` не хранит уроки — только этот файл.*
