# WORKFLOW.md — операционные механики

Императивные механики: сессия, волна, задача, close, чекпоинт. Сам цикл (brief → … → FINAL) и
меню HALT — в [PIPELINE.md](./PIPELINE.md). Жёсткие пределы — в [RULES.md](./RULES.md).
Обоснования с примерами — в `docs/`. Этот файл правило + одна строка «почему» + ссылка на
глубину, без дублирования.

Нумерация параграфов стабильна — task-файлы и промпты ссылаются на неё («§15.1», «§19»). Новый
раздел получает номер в конец логической группы, старые не переезжают.

## §1. Сессионный старт

Порядок чтения в начале КАЖДОЙ сессии, без исключений:

0. Handoff JSON, если есть и дан триггер владельца — первым, он свежее памяти.
1. `CLAUDE.md` → 2. `WORKFLOW.md`/`RULES.md` → 3. `ROADMAP.md` (голова) → 4. `REFERENCE.md` по
   необходимости.

Память отстаёт от диска — версии/HEAD/долг verify по диску (§22). «Продолжаю чужой контур» и
«обрабатываю готовый отчёт» — не исключения из ритуала. _Почему: сессия без ритуала обработала
готовый отчёт и заспавнила проверку без явной модели субагента — подставился дефолт харнесса
вместо канона._

## §2. Цикл эпика (карта → PIPELINE)

```
старт (§1) → brief (техлид+владелец) → одна команда оркестратору → автономно:
рекон → скоуп → фитч (§6) + self-audit A-G → волны (§4/§7) → close без merge (§8) → СТОП
→ приёмка владельца — единственный внешний стоп → GO → FINAL самим оркестратором → post-hoc verify техлида
```

Полная механика — `PIPELINE.md`; здесь только карта.

вверх: субагент → оркестратор → HALT-меню → владелец, не угадывается.

## §4. Цикл задачи внутри волны (субагент)

1. Прочитать task-файл целиком. 2. Прочитать реальный код зоны записи ДО правки (RULES R1), не
по памяти. 3. Unique-match edit, не позиция по номеру строки из чужого описания. 4. Верифицировать
каждый шаг командой DoD. 5. Прогнать DoD целиком перед коммитом. 6. Коммит по шаблону (что+почему,
не «wip»). 7. Отчёт: коммит, DoD `n/N`, блокеры явно.

Отчёт различает **VERIFIED** (сам увидел) и **DISPATCHED** (запустил, не дождался) — канон в
REFERENCE.md. Субагент никогда не пушит. Расхождение с task-файлом — стоп и отчёт, не
досочинение по аналогии.

## §5. Diag-then-fix (кратко; глубина `docs/05`)

Сложнее одного файла — diag отдельно от fix: diag добавляет временную инструментацию, собирает
данные с запасом, отчёт Симптом/Сбор/Анализ/Рекомендации, fix не применяется на этой фазе.
Синтез между ними — свежий взгляд оркестратора, не автор диагноза (тот защищает первое
правдоподобное объяснение). **Bounded self-heal ≤ 2** на гейт — тот же вердикт дважды → self-audit
+ повторный diag, не третья попытка. Два идентичных провала подряд → стоп и измерение держателя
ресурса, не слепой перебор параметров. _Почему: слепой ретрай на одинаковой ошибке — дорогой
способ не найти причину; она почти всегда внешняя._

---

## §6. Fitch: full vs lite

**Full** — контракт по ролям (аналитик/дизайнер/техлид/тестировщик/девопс), каждая роль `done`
или честный `not_applicable` с причиной; требования — **inline**, реальные формулировки и
конкретные команды wave-gate, не placeholder. Для UI/feature/security.

**Lite** — brief + PLAN + task-файлы без 5 ролей. Для инфра/cleanup/housekeeping.

Full/lite решает оркестратор с обоснованием в FITCH-PLAN/отчёте, не спрашивает разрешения отдельно.

---

## §7. Wave gate

Волна закрывается сама на зелёном machine-readable DoD, без стоп-подтверждения в чате между
волнами (см. §9).

1. Build green только через wrapper (§13). 2. Test green — узкий фильтр не закрывает close-гейт,
на волне объём по риску (§10). 3. Diff по failure-id: после минус до = пусто. 4. Post-wave
verify — отдельный субагент, не самоотчёт исполнителя. 5. Verify по диску (§22) критичных
заявлений.

Красный после двух self-heal (§5) → HALT, не третья попытка. **Fix-in-wave**: баг прошлой волны,
пойманный текущим гейтом, чинится в этой же волне. _Почему отменена confirmation между волнами:
она душила автономный прогон уже проверенного self-audit'ом пакета — 10 подтверждений за сессию
вырождались в ритуальное «ок»._

---

## §8. File isolation в волне (кратко; глубина `docs/06`)

Два субагента одной волны не трогают один файл — race на read-modify-write. Резолвы: sequential
в одной волне, перенос в следующую, декомпозиция файла на модули до старта эпика. Владение
объявлено явно в КАЖДОМ task-файле. Точка входа приложения / общие синглтоны — одна задача за
волну.

---

## §9. Человеческие гейты (карта → PIPELINE §9)

Один внешний стоп — приёмка владельца перед merge; GO = оркестратор сам выполняет FINAL.
HALT-форки — по фиксированному меню из брифа (новая зависимость / архитектурный сдвиг /
продуктовое решение / красный после 2 self-heal / нарушение sacred-инварианта), не по
произвольному усмотрению. Прежняя модель — подтверждение после КАЖДОЙ волны — упразднена (§7):
душила автономный прогон пакета, уже прошедшего self-audit до кодинга. Полная механика —
`PIPELINE.md` §9.

---

## §10. Smoke policy

Волны: объём по риску, узкий прогон допустим для диагностики, не для close-гейта. **Close — ОДИН
полный прогон обязателен**, не три «для надёжности» и не ноль «сэкономить время». Флейк — только
при `n ≥ 5` с явным соотношением; одно красное наблюдение — красное наблюдение. Лог парсится
**скриптом**, не глазами построчно; путь `tee` — явный в команде. Соло-зелёный конкретного теста
не отменяет его красноту в полном прогоне — красный относится к своему классу
(транзиент/дефект), не «лечится» отдельным запуском без причинного контроля. _Почему: «N passed»
без committed-лога и exit-кода — пересказ, не пруф._

---

## §11. E2E / рантайм-гигиена сессии

Порядок: **build → cleanup → smoke**, обратный недостоверен. 1. Свежий бинарь — собран после
последнего коммита волны. 2. Чистое персистентное хранилище — ВЕСЬ каталог состояния, не только
JSON: кеш/localStorage/встроенная БД конфликтуют между прогонами. 3. Изолированный идентификатор
сборки под тесты — тестовый рантайм не пишет в каталог реального пользователя. 4. Закрыты
процессы предыдущего прогона.

### §11.1. Async UI assertion timing

Store/эффект-driven UI — синхронный callback не дожидается перерендера. «Записать → пауза →
прочитать» — в ДВУХ раздельных вызовах исполнения, не в одном блоке.

### §11.2. Build ≠ smoke

Два явных шага с раздельными логами, не один вызов — иначе ошибка сборки тонет в шуме тестового
вывода и даёт ложный диагноз.

---

## §12. Ветки, worktree, рабочие каталоги

Ветка на эпик: `feature/<epic-id>-<slug>`; merge только `--no-ff`; после — удалить ветку локально
и на origin. **Один каталог — один владелец** активной задачи, чужой `checkout`/`switch`/`reset`
в общем дереве запрещён «даже на минутку». Параллельная работа — только `git worktree add` +
`remove`/`prune`; ревью чужого PR — всегда в worktree. Pre-flight: `git branch --show-current` ==
ожидаемая ветка, расхождение — стоп и доклад, не молчаливый возврат. Финиш — своя ветка или
снятый worktree, «оставил на главной» недопустимо. Прерванная операция — стоп-доклад с фактическим
состоянием. **Тестовый прогон называет измеренное дерево** (путь/worktree + HEAD) — без этой
строки не доказано, какое дерево измерено. _Почему: чужой checkout под активным эпиком и брошенный
merge без доклада — два независимых инцидента за сутки, оба стоили часов диагностики._

## §13. Build system discipline

Все сборки — ТОЛЬКО через wrapper-скрипты проекта, субагент никогда не вызывает toolchain
напрямую. Wrapper несёт guard'ы (версия рантайма, env-флаги) и cleanup — прямой вызов теряет их и
ломает воспроизводимость. Имена скриптов — `docs/09-runtime-cookbook.md` (per-stack), этот файл
stack-agnostic.

## §14. Скиллы

`SKILL.md` читается ПЕРЕД использованием, не угадывается по названию папки. Скиллы — роли внутри
пайплайна, каждый — папка с `SKILL.md` + опциональные шаблоны/скрипты. Для внешних участников —
`kit/skills/` (глубина `docs/07`).

## §15. Definition of Done

DoD — **одна команда с machine-readable выводом**, не «код написан»/«работает». Хорошо:
`<cmd> | grep -c "0 failed" >= 1`; `<unit-cmd> <module>` → `N passed; 0 failed`; `grep -c
"<точная сигнатура>" <файл> == 1`. Плохо: «тесты проходят», «сборка чистая» — не
третье-лицо-проверяемо. **Exit-код читается ДО доверия к stdout** — обёртка на части платформ
возвращает свой код, не код обёрнутой команды (глубина `docs/10`). **Grep аккуратно**: декларация
и экспорт — одна строка совпадения, не два. Идентификатор task-файла сверяется с реальным кодом
ДО написания (RULES R1) — дрейф имени/id — частый источник ложно-зелёного гейта.

## §16. Scope discipline

Не чинить «заодно» вне scope. Не расширять fix сверх найденного diag'ом (§5). Не писать «N
исправлено», если часть отложена честно — явный пункт known-issues + пул пикапов (§0), не
растворяется в общей цифре. Находка глубже тикета — зафиксировать с доказательством и спросить,
не расширять молча. Сомнение в границах — вопрос владельцу, не додумывание. Для
миграционных/housekeeping эпиков — категоризация ВСЕХ источников (прод / тесты / фикстуры /
конфиги) до брифа, не только очевидной категории.

---

## §17. Красный тест и RED→GREEN

Регрессионный тест — КРАСНЫЙ на непочиненном коде (пересборка между прогонами обязательна) и
ЗЕЛЁНЫЙ после фикса. Несколько защитных слоёв — нейтрализовать верхний перед тестом нижнего,
иначе тест валидирует не тот слой. Тест, зелёный при мутации защищаемой строки, — провалившийся
тест: приёмка независима от автора. Никогда не прятать/ослаблять/удалять красный тест вместо
диагностики. Глубина с примерами — `docs/05`.

---

## §18. Триангуляция аудита (in-flight)

Несколько субагентов параллельно в разных ролях (архитектор/инженер/скептик, опц. security/QA);
синтез по уровню согласия: **триангулировано** (3+ источника) — твёрдый блокер; **вероятно** (2,
верифицировано кодом) — высокий приоритет; **соло** (1, верифицировано вручную) — бэклог.
Findings без верификации кодом не применяются, отклоняются явно с причиной. Глубина —
`docs/04-audits-triada.md`.

---

## §19. Команда оркестратору и промпт субагенту

Команда техлида оркестратору — ОДИН fenced-блок, самодостаточный. Тело инструкции — в файле
(PLAN/task), не в чате. Промпт субагенту отсылает к task-файлу как единственному источнику
истины, не пересказывает его. Patch vs rewrite: корректировка task-файла — 1–2 идентификатора
правится пометкой в промпте; больше — task-файл переписывается целиком (источник истины — файл,
не промпт); многоточечная правка JSON-контракта — только полная перезапись + валидация. Для
карточек внешнего контура — фиксированная строка: «прочитай и исполни карточку `<path>`,
отчитайся по разделу Return» (глубина `docs/12`).

## §20. Housekeeping

Короткие эпики между фичами: очистка диска, синхронизация доков, архивные переносы, pre-flight
перед крупным эпиком. 1-2 коммита. Baseline гейтов после — без изменений. Чек-лист — `docs/08`.

---

## §21. Handoff и чекпоинт

Handoff JSON держит снимок состояния между сессиями: identity, current_state, awaiting_owner,
next_session_first_steps, incidents_open, tooling_notes, patterns_reminder (см.
`templates/handoff.json`). Пишется **целиком** (snapshot, не точечная правка), verify чтением
сразу после записи. Триггеры: ключевой шаг завершён, сжатие контекста, конец сессии. Владение
секциями: identity/tooling — при смене инструментария; current_state/awaiting_owner — на каждом
стопе; next_session_first_steps — обязательно перед концом сессии. **Таймстампы — UTC ISO-8601**
— локальные штампы выглядят как разрыв во времени или идут немонотонно.

---

## §22. Verify по диску

Заявления («прогон N/M», «файл создан», «merge выполнен») — заявления, не факты. Критичное лид
проверяет сам: smoke-метрики — реальный committed лог, не пересказ; артефакты — размер/mtime, не
подпись в отчёте; merge/tag — состояние веток читается напрямую; файлы — листинг, не память.
Канон «число без транскрипта не существует» — REFERENCE.md, не повторяется здесь. Расхождение —
норма («поправка: реально X») — важен факт, не разбор чужой ошибки.

---

## §23. Рекон и self-audit A–G

Рекон — рой независимых субагентов внутри оркестратора (несколько ролей параллельно),
триангуляция «3+ = твёрдо» + adversarial-проверка утверждений об отсутствии. Одиночный
inventory-проход НЕ заменяет рой — одна перспектива не ловит composition-дефекты. Self-audit
A–G — свежий adversarial-субагент аудирует пакет (contract+PLAN+task-файлы) ДО первой волны: A.
Покрытие требований. B. Реализуемость (сигнатуры совпадают с кодом). C. File isolation. D.
Порядок волн. E. DoD-грепы не ловят ложно-зелёный. F. Инварианты соблюдены. G. Edge-кейсы.
HIGH-находка — блокер W1 с точным местом и правкой. Фолд — компактный список патчей до старта
волн, не отдельный документ на десятки страниц.

---

## §24. Версия и целостность артефактов (lockstep)

**Все источники версии — в ОДНОМ коммите** (полный список — в `CLAUDE.md` проекта). Lock-файлы —
результатом сборки, не рукой. После литерального version bump — grep кодовой базы на старую
строку: слепая глобальная замена портит исторические упоминания и пропускает файлы вне шаблона —
каждое совпадение просматривается вручную. **Timestamp-гейт**: mtime артефакта против последнего
CODE-коммита, НЕ version-bump коммита (сборка часто идёт до bump'а). sha256 — в отчёте, артефакты
с префиксом платформы и версией в имени.

---

## §25. Гигиена артефактов процесса + реестры FINAL

Два класса: **знание** (committed навсегда) и **процесс** (временное, gitignored). При close:
физический prune процесс-артефактов (`git rm` не подметает untracked), рекурсивные
gitignore-паттерны, чистый `git status`. **Реестры — ОДНИМ прогоном из ОДНОГО списка** (все в
одном коммите close/FINAL) — частичное обновление — рецидивирующий класс «реестры отстают».
Уроки — два последних эпика в REFERENCE.md, старше — в архив (§29).

## §26. Модели и спавн субагентов

**Каждый спавн, на любом механизме — с явным параметром модели.** Наследование модели вызывающего
или дефолт харнесса запрещены даже при случайном совпадении результата. Файлы определения агентов
читаются один раз в начале сессии — правка посреди сессии не подхватывается.

Опциональное расщепление по уровню (решение владельца, не default): closed-world проверки —
дешёвому уровню, суждение/синтез/приёмка — основному; фолбэк на основной после 2 однотипных
провалов; каждое утверждение дешёвого уровня перепроверяется, ведётся per-model «линейка».
Типичные ошибки дешёвого уровня: не тот файл при относительном пути; строки не тому файлу;
пересказ вместо точного вывода; усечённые списки без пометки; открытый аудит на ложной посылке.

_Почему: сессия обработала готовый отчёт и заспавнила проверку общим методом без явной модели —
унаследовала модель сессии вместо канона исполнителей; дефолт харнесса победил канон, потому что
ни один текст явно не запрещал именно этот путь вызова._

## §28. Байтовая гигиена текстовых артефактов

**UTF-8 без BOM, LF**, всегда. Никогда не писать файлы репозитория командлетами оболочки,
эмитирующими BOM/UTF-16 — правки только через edit-инструмент или закоммиченный скрипт, не
inline-однострочником (спецсимволы ломают точное совпадение). Проверка: EOL-режим файлов (ни
одного «бинарного»/CRLF там, где должен быть LF); первые байты ≠ сигнатура BOM; байтовый
(не кодпоинт) скан на mojibake — кодпоинт-грep слеп к невалидным байтам. Логи между ОС —
сравнение через объект системы контроля версий, не рабочую копию. _Почему: класс BOM/mojibake
рецидивировал пять раз подряд на новых файлах — только байтовый скан на каждом коммите закрывает
класс, а не конкретный подведший файл._

## §29. Документы: канонический дом, диета контекста

Каждая единица знания — в одном доме; повторное упоминание — 1-2 строки + «_см. канон:
`<path>`_», не копия. Диета контекста: файл читается диапазоном/фильтром, не целиком, особенно
сразу после сжатия контекста (файл не изменился — изменилась только память сессии); вывод
инструментов усекается у источника. Глубина, включая опциональную инверсию доков в базу знаний —
`docs/14-knowledge-and-context.md`.
